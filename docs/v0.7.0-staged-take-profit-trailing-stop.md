## 1. 背景

v0.4.0 的保护模型很简单：`TAKE_PROFIT_MARKET` + `STOP_MARKET`，两张都是 `closePosition=true`。
它的两个好处都来自 `closePosition`：**触发时平掉当时剩余的全部仓位**，以及**仓位归零时另一张由交易所
自动撤销**。后者让 executor「不轮询、不盯市」，进程崩了也不会留下裸奔仓位。

这个模型有一个策略上的短板：**一次走完**。要么在固定倍数上全部兑现（常常太早，把大趋势的仓位砍掉一半），
要么一路拿到固定止损（常常太晚，把浮盈全吐回去）。本仓库现在既没有分批减仓的口子，也没有
移动止损的口子。

要加这两个口子，就必须先放弃 `closePosition` 的一个好处——这是本期的全部难点所在：

> `closePosition` 与 `quantity` / `reduceOnly` **互斥**（同时发是 `-1106`）。也就是说
> **条件单没法只平一半**。分批止盈必须改用带 `quantity` 的条件单，而带数量的单
> 不再享有「仓位归零时自动撤销」。

因此本期不是「加两个参数」，而是**换一种保护形态**，并把它换掉之后丢掉的那份保证，用可论证的
方式补回来（§3 R-4、R-9）。

## 3. 需求条目

### R-1 两段模型

- **R-1.1** 开仓后挂两张单，形态与 v0.4.0 不同：
  - **止损**：`STOP_MARKET` + `closePosition=true`（**保持不变**）。它保护的是**当时剩余的全部仓位**，
    因此第一段减仓之后它**继续有效**，不需要因为减仓而重挂。
  - **第一段止盈**：`TAKE_PROFIT_MARKET` + `quantity = q1` + `reduceOnly=true`，**不带** `closePosition`
    （官方参数表已确认这三者合法，附录 E.2 / E.3；Request Weight 1）。
  - **比例的三个取值走三种形态**（详见 R-2.5）：`ratio = 0` 与 `ratio = 1` 都退回 `closePosition=true`，
    即 v0.4.0 的形态——因此「不分批」与「全平」都**不放弃**交易所自动撤单的保证。
- **R-1.2** 「两张要么都挂上要么都不挂」的既有不变量（§6.3 第 5 条）**继续适用**，失败回滚顺序不变。
- **R-1.3** 剩余仓位**不设固定止盈**。它的自动出口只有移动止损。

> 为什么止损坚持用 `closePosition` 而不改成带数量：带数量的止损在第一段减仓后数量会对不上
> （触发时要么不够平，要么在无 `reduceOnly` 保护下反向开仓）。而 `closePosition` 的语义是
> 「触发时平掉当时剩余的全部」——这恰好就是移动止损每一档都需要的东西。

### R-2 第一段的量与价

- **R-2.1** `q1 = alignToQty(filledQty × takeProfit1Ratio, stepSize, 'down')`。
  `stepSize` 取 `contract_spec.raw.filters[].LOT_SIZE.stepSize`（新增 `parseStepSize`，与 `parseTickSize`
  同款解析与同款「步长整数倍而非小数位数」对齐）。
- **R-2.2** `q1` 必须满足 `0 < q1 < filledQty`，否则**拒绝这一段**并留可见失败记录。
  取整后等于 0（极小仓位）**不许**悄悄改成「不减仓」，也不许退化成全平。
- **R-2.3** 第一段止盈价 `tp1Price = entryPrice ± takeProfit1AtrMult × ATR(入场时刻)`，对齐方向朝远离入场价。
- **R-2.4** `takeProfit1Ratio > 0` 时必须校验 **`tp1Price` 比 `takeProfitPrice` 更靠近入场价**，
  否则 `CONFIG_INVALID`。两个倍数配出「第一段比整段止盈还远」是自相矛盾的配置，必须在算价时就拒。
- **R-2.5** **比例是策略参数，在页面上可设**（`RiskPolicyPanel` 的全局与标的两个作用域都可填），
  取值 `[0, 1]`，页面用 0–100 的百分数呈现。三个取值走**三种形态**，只有中间那个进 `trailing`：

  | 取值            | 止盈单形态                                      | 剩余仓位    | 进 `trailing`？ |
  | --------------- | ----------------------------------------------- | ----------- | --------------- |
  | `ratio = 0`     | `closePosition`（= v0.4.0）                     | 无          | 否              |
  | `0 < ratio < 1` | `quantity = q1` + `reduceOnly`                  | `1 − ratio` | **是**          |
  | `ratio = 1`     | `closePosition`（用 `takeProfit1AtrMult` 的价） | 无          | 否              |

  `ratio = 1` 因此**比 80% 更简单**：它直接退回 v0.4.0 的形态，交易所自动撤单的保证一分不丢，
  也不需要移动止损与定时器。`ratio = 0` 与 `ratio = 1` 的区别只在**用哪个倍数算止盈价**
  （`takeProfitAtrMult` vs `takeProfit1AtrMult`）。

- **R-2.6** 百分数与小数之间的换算**只有一处实现**（一个 `ratioToPercent` / `percentToRatio`，
  放在 `packages/core`），控制面与 CLI 都用它。**不许**在前端输入框里 `÷ 100` 了事、
  再让后端与 DB 各存一份口径（§6.4 第 4 条治的正是这个）。

### R-3 移动止损的口径（纯函数，`packages/core/src/risk-policy.ts`）

多头（空头完全镜像）：

```
cand = alignToTick(extreme.high − trailAtrMult × atrNow, tickSize, 'down')
stop = max(prevStop, cand)            // 棘轮：只上移
breakeven = alignToTick(entryPrice + breakevenOffsetAtr × atrNow, tickSize, 'up')
stop = max(stop, breakeven)           // 仅在第一段兑现后应用
```

- **R-3.1** 输入等长无关（不是序列函数）：`{side, prevStop, extreme, atr, entryPrice, tickSize, trailAtrMult, breakevenOffsetAtr}`，
  输出 `{stopPrice, changed, reason}`。不读时钟、不做 IO、不用随机数（§5 第 4 条）。
- **R-3.2** `changed=false` 时**不得触发任何挂撤**。这是控制频率的主要手段（附录 E.3 的限频估算依赖它）。
- **R-3.3** 对齐方向钉死：候选价向下取整（`down`），保本位向上取整（`up`）。半 tick 的差别足以让
  「刚挂上就必被扫」（§6.3 已有结论），移动止损每一档都要重犯这个错误，所以要各有断言用例。

### R-4 重挂时序：先挂新、再撤旧

- **R-4.1** 止损档位需要移动时，顺序固定为：**挂新止损 → 撤旧止损 → 回填 `sl_algo_id`**。
  绝不允许先撤后挂——那会造出一个无保护窗口。
- **R-4.2** 理由必须写进代码注释：两张 `closePosition` 单在重叠期内即使都被触发，
  最多得到一次「无仓可平」的拒绝，**不会开出反向仓位**（`closePosition` 的语义就是只平不开）。
  短暂双挂的风险因此远小于短暂裸奔。
- **R-4.3** 撤旧失败：挂上新单但撤不掉旧单 → **不推进档位**（`sl_algo_id` 仍是旧的），
  记 `trail_last_error` + `log.warn`，下一轮重试；**不允许**把它当成功。
  两档止损同时存在期间，账面上以旧档为准（保守），控制面必须显示「有重叠止损单」。
- **R-4.4** 挂新失败：旧单仍在，**仓位保持受保护**，同样记可见原因。不回滚、不撤旧。

### R-5 状态机

`risk_bracket.state` 追加两个值（**只追加**，既有五个值语义不变）：

| state           | 含义                                        | 交易所上应存在   | 未终结 |
| --------------- | ------------------------------------------- | ---------------- | ------ |
| `armed`         | 不分批，两张 `closePosition`（v0.4.0）      | TP + SL          | 是     |
| `partial_armed` | 第一段 `quantity` 单 + `closePosition` 止损 | TP1 + SL         | 是     |
| `trailing`      | 第一段已成交，剩余仓位在移动止损中          | **只有 SL 一张** | 是     |
| `take_profit`   | 一次性止盈成交（不分批时）                  | 无               | 否     |
| `stop_loss`     | 止损成交（含移动止损成交）                  | 无               | 否     |
| `cancelled`     | 工具外平仓                                  | 无               | 否     |
| `failed`        | 没挂上任何单                                | 无               | 是     |

- **R-5.1** `trailing` 阶段**只挂一张止损单**。第一段止盈单成交后由交易所自动消失，不需要本地撤。
- **R-5.2** **不新增 `stage` 列**。阶段由 `state` 表达；再加一列阶段就是第二套状态，
  与 §6.1 第 2 条治的病同型。
- **R-5.3** `trailing` 行的 `atr` / `stop_price` / `take_profit` 列**保持入场时的值不变**——
  它们记的是「第一段为什么这么算」。移动中的那一档写在 `trail_stop_price`，两者不可互相覆盖。
- **R-5.4** 阶段转换一律**先落库意图、再动交易所**，顺序与 §6.3 第 4 条同源：
  TP1 成交事件到达 → 先把该行置为 `trailing` + 写入极值与保本档位 → 挂新止损 → 撤旧 → 回填。
  进程死在中间时，对账会看到 `trailing` 但没有止损单，报 `missing-stop-order`（紧急）。

### R-6 极值取数

- **R-6.1** `quant_data.risk` 的摘要增加 `extreme: {high, low, from, to}`：**持仓期**（`entryTime` 到 `asOf`）
  **极大连续段**内的 `high` 最大值与 `low` 最小值。ATR 仍用它自己的窗口段；两者**各自**遵守
  「不跨缺口」（§6.3 第 2 条），互不影响。

  > **实现期的两处口径修订**（2026-10-17 已落地；登记在这里是为了不被当成笔误）：
  >
  > 1. **极值取的是 ATR 那个周期的 high/low，不是固定 1m。** 因为 R-6.2 要求「一次取数」，
  >    而 `atrInterval` 可配（15m / 1h / 4h / 1d）；两条同时满足只有「同周期取一次」一种做法。
  >    **executor 缺省 `atrInterval = 1m`，此时与本条原文的 1m 口径完全一致**；配成高周期时
  >    极值是那个周期的高低——这是「一次取数」优先于「固定 1m」的取舍。
  > 2. **下界是 `time >= entryTime`，不含入场那一根 1m。** 成交发生在该根中途，把它的 high
  >    算进极值会把**入场前的影线**当成持仓期高点，移动止损会因此偏宽。代价是漏掉入场那一
  >    分钟的成交后冲高——相比「止损位一开始就松一截」，这个方向更安全。

- **R-6.2** **一次调用同时返回 ATR 与极值**，不许分两次取数：两次取数之间可能落进一根新 bar，
  于是「极值」与「ATR」来自两个不同的时刻，公式失去意义。
- **R-6.3** `atr_at` 的 `entryTime` 形参是**必填**。拿不到持仓期起点就算不出极值，
  **不许默认成 0 或用窗口起点顶替**（§5 第 8 条）。
- **R-6.4** 极值段短于持仓期时，`extreme.from/to` 必须如实回传，让调用方知道它短了；
  缺口**不许插值**（v0.1.0 R-11.10）。
- **R-6.5** 极值取不到（持仓段内一根连续 K 都没有）时：本轮**不移动止损**，保留上一档，
  记 `trail_last_error` + `log.warn`，并在控制面显示。它不是 `RISK_ATR_UNAVAILABLE`——
  ATR 拿不到要**拒绝下单**，极值拿不到只是本轮不调整，两者严重度不同，**不许混成一个码**。

### R-7 止损越过现价时的保守取舍

`cand >= 参考现价`（多头）意味着极值已经回撤到吃掉全部浮盈，此时挂上去会**立刻触发**。

- **R-7.1** 本期**不挂**新档、保留旧止损、记可见原因（「移动止损位已越过现价，本轮不调整」）。
- **R-7.2** 这是**有意的保守选择**，不是兜底：移动止损位的语义是「保护浮盈」，而此时已无浮盈可保护；
  此时平仓属于策略决策（严格追踪，N-5），不该由一个本来只负责「挪止损」的程序顺手做掉。
- **R-7.3** 参考现价取库内最新已收盘 1m 的 `close`（滞后不超过一根 K 线）。**不引入** markPrice 流：
  那会让 executor 多一条流与一套重连逻辑，而它只用来做一个粗判。

### R-8 幂等与崩溃恢复

- **R-8.1** TP1 成交事件**会被重放**（listenKey 续期、断线重连）。`trailing` 或终态的记录再次收到
  TP1 事件时：**直接返回，不得重复挂单、不得重复推保本位**。现有 `settle()` 会把任何状态
  `markBracketSettled('take_profit')` 覆盖成终态——那会把 `trailing` 抹成「已了结」，
  **这是本条要防的头号回归**，改造点见附录 E.5。
- **R-8.2** 移动止损定时器**只重放自己的意图**：它可以重试「已落库的 `trailing` 行」的重挂，
  因为那是对**已提交**意图的续做；它**不修复**自己在对账里发现的漂移（例如 `position-without-record`），
  那些仍然只报告（§6.5 第 1 条）。
- **R-8.3** 定时器**不新增常驻进程**、不新增出网取价。它与对账定时器**分开**：
  对账只读（§6.5 第 1 条），移动止损要下单。两者共用一个定时器会让「只读」这条保证失守。

### R-9 丢掉「自动撤单」之后的补偿

- **R-9.1** 分批形态下，仓位被工具外平掉时，第一段 `quantity` 单**不会**由交易所自动撤销
  （它只按数量平仓，而仓位已经是 0）。必须由 executor 在**净额归零**的既有路径上撤单
  （`closeOutside`，`service.ts`），并在撤单失败时记 `trail_last_error`。
- **R-9.2** **进程不在时无人撤单**。这是相对 v0.4.0 的实质回退，必须在 `apps/executor/README.md`
  里**照实改写**那段「进程崩了也不会留下裸奔仓位」的保证，而不是留着旧句子。
- **R-9.3** 补偿由**对账**暴露而不是修复：新增差异类型 `unexpected-take-profit-order`
  （`trailing`/`cancelled` 行却在交易所查到 TP 单，warning），严重度分档见 `README.md` 的对账表。

### R-10 对账判据按阶段分流

- **R-10.1** `missing-take-profit-order` **只对 `armed` 生效**。`trailing` 阶段本来就没有止盈单，
  按旧判据会每轮报一条假警报——而假警报是让报告整体失去可信度的最快方式（§6.5 第 2 条）。
- **R-10.2** `price-mismatch` 对 `trailing` 行必须比 **`trail_stop_price`**（当前生效档位），
  不是 `stop_price`（入场档）。这一条不做，移动止损每调一档就会报一条价格不符。
- **R-10.3** `UnsettledBracketState` 扩为 `'armed' | 'partial_armed' | 'trailing' | 'failed'`。

### R-11 策略参数

`executorSchema` 与 `risk_policy` **同时**增 5 项，取值范围照抄（§6.4 第 4 条：页面校验、schema
CHECK、纯函数校验三处不许各写各的）：

| 参数                 | 类型 / 范围                 | 缺省     | 作用                                                                                          |
| -------------------- | --------------------------- | -------- | --------------------------------------------------------------------------------------------- |
| `takeProfit1Ratio`   | `[0, 1]`                    | `0`      | `0` = 关闭分批；`1` = 全平；`(0,1)` = 减仓该比例，剩余交给追踪。**页面上以 0–100 百分数填写** |
| `takeProfit1AtrMult` | `(0, 50]`                   | `3`      | 第一段止盈倍数                                                                                |
| `trailAtrMult`       | `(0, 20]`                   | `2`      | 移动止损倍数 k                                                                                |
| `breakevenAfterTp1`  | `boolean`                   | `true`   | 第一段兑现后止损是否上移到保本位                                                              |
| `trailIntervalMs`    | `≥ 0`（`0` = 关闭自动重算） | `60_000` | 移动止损重算周期                                                                              |

- **R-11.1** 缺省合并规则**只有一份实现**，写在 `resolvePolicy`：配置里没写 `takeProfit1AtrMult`
  时取 `takeProfitAtrMult` 的值、没写 `trailAtrMult` 时取 `stopAtrMult` 的值。
  这是「同一个参数的两个名字」的显式声明，**不是回落、不是猜**；控制面保存策略时要求**显式给出**这两个字段，
  因此库里永远存着具体数值。
- **R-11.2** 缺省 `trailIntervalMs = 60_000` 的依据是限频：一轮里每个 `trailing` 记录 1 次挂 + 1 次撤，
  而 R-3.2 的「价未变就不动」让绝大多数轮次为零动作。详见附录 E.3。
- **R-11.3** 迁移里所有新列的 `DEFAULT` 必须与 `executorSchema` 的缺省**逐字相同**。
  两处不一致时，库里旧行读出来的行为会与新建行的行为不同——而这种差异只在数据量大时才显形。

## 4. 迁移与表结构方案

详见附录 C 的 DDL 草案。硬性约束：

- 唯一来源是 `packages/data/sql/010_risk_trailing.sql`（**追加**，不改动 `006` 的文件）。
- 必须**幂等**（每个入口启动都会跑一遍）：`ADD COLUMN IF NOT EXISTS` + `DROP CONSTRAINT IF EXISTS`

  与 `quote_volume` / `trades` 的「交易所未提供」**不是一回事**（§5 第 2 条），注释里写死这一点。

## 7. 验收标准

| 编号  | 验收                                                                                                                                                       |
| ----- | ---------------------------------------------------------------------------------------------------------------------------------------------------------- |
| AC-1  | `takeProfit1Ratio = 0` 时，全部既有测试**一行不改**通过，且 executor **不发起**任何移动止损挂撤                                                            |
| AC-2  | `0 < ratio < 1` 时，第一段止盈请求带 `quantity` + `reduceOnly` 且**不带** `closePosition`；止损请求带 `closePosition` 且**不带** `quantity` / `reduceOnly` |
| AC-3  | `q1` 按 `stepSize` 向下取整；取整后 `q1 <= 0` 或 `q1 >= filledQty` 时拒绝并留可见记录                                                                      |
| AC-4  | `takeProfit1Ratio > 0` 且 `takeProfit1AtrMult >= takeProfitAtrMult` 时抛 `CONFIG_INVALID`                                                                  |
| AC-5  | `deriveTrailingPlan` 满足：候选价向下对齐、保本位向上对齐、`stop >= prevStop`（多头）、价未变时 `changed=false`                                            |
| AC-6  | `cand >= 参考现价`（多头）时不挂新档、不撤旧档、记可见原因                                                                                                 |
| AC-7  | 档位需要移动时，**调用顺序断言为「挂新 → 撤旧」**；撤旧失败时 `sl_algo_id` 不变且有 `trail_last_error`                                                     |
| AC-8  | TP1 成交事件重放两次，只发生一次重挂，第二次返回幂等结论（现有 `settle()` 的覆盖行为被修复）                                                               |
| AC-9  | 进程在「已落库 `trailing`、未挂新止损」处崩溃后重启，定时器补挂成功，且对账在补挂前报过 `missing-stop-order`                                               |
| AC-10 | `trailing` 行不再被 `missing-take-profit-order` 报出；其价格比对用 `trail_stop_price`                                                                      |
| AC-11 | `010_risk_trailing.sql` 连跑两次不报错；新列 DEFAULT 与 `executorSchema` 缺省逐字相同                                                                      |
