## 1. 背景

v0.1.0 把 1m 拉全并固化进 `klines_1m`：表名即「只存 1m」的决定（v0.1.0 R-6），
N-1 明确「不做 1m 以外的周期与周期聚合」。本期把这个决定反过来：高周期**存在**了，但**只由库内 1m 派生**。

为什么必须同源：

1. **一根 4h 蜡烛只能有一个来源**。若改用交易所的 `/fapi/v1/klines?interval=4h`，同一根桶会有两套数据，
   而两者的边界与成交量口径并不保证逐值相等；此后「图上不对」将无法判定是同步错了还是聚合错了。
2. **派生是本地计算，不花配额**。交易所高周期接口要额外请求与权重，而库内 1m 已经是权威。
3. **三条既有语义必须原样上推**：缺口不得插值（v0.1.0 R-11.10）、库里不存未收盘 bar（R-10.1）、
   NULL 表示「交易所未提供」而非 0（R-4）。高周期若不继承这三条，就会变成一层「看起来正常」的假数据。

## 3. 需求条目

### 3.1 派生存储

#### R-1 schema 与迁移

1. 新增 `packages/data/sql/004_klines_agg.sql`：**幂等、可重复执行、空库可一路迁到最新**
   （v0.1.0 R-1.1 / R-1.2 继续成立）；迁移文件仍是 schema 的**唯一来源**（R-2.5）。
2. 四张派生表，表名即「周期 → 表」映射的唯一来源：

   | 表           | 周期 | 桶宽 W (ms) | 每标的每年桶数（算术推导，附录 B.1） |
   | ------------ | ---- | ----------- | ------------------------------------ |
   | `klines_15m` | 15m  | 900 000     | 35 040                               |
   | `klines_1h`  | 1h   | 3 600 000   | 8 760                                |
   | `klines_4h`  | 4h   | 14 400 000  | 2 190                                |
   | `klines_1d`  | 1d   | 86 400 000  | 365                                  |

3. 每张表的列必须与 `klines_1m` **逐列一致**：`symbol` / `time` / `open` / `high` / `low` / `close` /
   `volume` / `quote_volume` / `trades`，类型与 NULL 语义一致（v0.1.0 R-4）。
   `time` 是**桶起点**（epoch 毫秒）；主键 `(symbol, time)`；加 `(symbol, time)` 的 BRIN 索引（与 1m 同形）。
4. **不得改动 `klines_1m`**：不加列、不改主键、不动 BRIN。派生表必须能整表清空重建而不影响 1m（R-5）。
5. 派生表**没有水位列、也没有状态表**：聚合进度由 1m 数据与 R-3 判据推导。
   新增第二套「同步到哪里」的概念正是 v0.1.0 R-9.6 明确要避免的。
6. 不得让两侧各持一份表名映射：`packages/core` 与 `quant_data` 各有一份「周期 → 表名」映射，
   必须有测试断言二者与迁移文件里的表集合**三方一致**（AC-1）。
7. 周期集合本期固定四个，但**桶对齐与覆盖判据必须按桶宽 W 参数化**，加入 5m 时不得需要改判据本身。

#### R-2 聚合语义

1. **桶对齐**：`bucket_start(t, W) = t - (t mod W)`（`t` 为 epoch 毫秒）。四个 W 都整除 86 400 000，
   且 epoch 0 是 UTC 零点，因此所有桶天然落在 **UTC 边界**上：1d = UTC 00:00，4h = 00/04/08/12/16/20，
   1h = 整点，15m = 00/15/30/45。
   不得引入本地时区、交易所时区或 `timestamptz`（v0.1.0 R-1.6 的时间口径不变）。
2. **聚合公式**（桶内按 `time` 升序的 1m 行 R）：
   - `time = bucket_start`
   - `open = R.first.open`，`close = R.last.close`
   - `high = max(R.high)`，`low = min(R.low)`
   - `volume = sum(R.volume)`
   - `quote_volume`：**任一 R 的该列为 NULL → 结果 NULL**；全部非 NULL 才求和。`trades` 同规则。
   - 理由：v0.1.0 R-4.2 定义 NULL =「交易所未提供该字段」。对一部分行求和、把另一部分当 0，
     都会产出一个**看起来正常**的错数（R-4.3 明确禁止）。桶级 NULL 是唯一诚实的表达。
3. 不得插值、不得用均价或前收顶替、不得跨桶借数据、不得用交易所的高周期接口对账（N-2）。
4. 聚合是**纯数据变换**：同一组 1m 行必得同一组桶——无时钟、无随机、无网络。
   R-3 判据同样只依赖库内 1m，因此整个派生过程可在测试里逐值断言（AC-2）。
5. 不做额外舍入、不把 `double precision` 转成 `numeric`：派生值与 1m 的差异必须只来自聚合本身。

#### R-3 收盘与覆盖判据（核心）

对某标的，记 `F = min(time)`、`L = max(time)`（该标的所有 1m 行）；对桶窗口 `[b, b+W)`，`b = bucket_start`：

- 有效窗口 `win = [max(b, F), min(b + W - 60_000, L)]`
- 期望根数 `expected = (win.end - win.start) / 60_000 + 1`（`win` 非空时）
- 实际根数 `actual = count(1m rows where time between win.start and win.end)`
- 已收盘 `closed = (b + W) <= (L + 60_000)`

1. **只有 `closed 且 actual == expected 且 actual > 0` 才写桶**；否则不写。
2. 判据**只依赖库内 1m 数据，不读本地时钟、不注入 `now`**。v0.1.0 R-10.3 那类时钟分叉
   （轮首时钟 / 现读时钟 / 长轮次误判）在这里从根上不存在；代价是「刚收盘但还没同步入库」的桶
   要等这批 1m 落库才出现——这正是期望行为，而不是缺陷。
3. **不得把未收盘桶先写进去再覆盖**：派生表在任一时刻都只含已收盘桶。
   这是 v0.1.0 R-10.1「库里不存未收盘 bar」在高周期上的同一条规则。
4. 有效窗口让两种边缘**不需要特例**：
   - **onboard 首日**：SOLUSDC 的 `onboardDate` 是 2024-01-03T12:45Z，当天 1d 桶的 `win` 从 12:45 起，
     期望根数是 **675** 而不是 1440，因此该桶**应当**写入，而不是因为「不满一天」永远缺席（附录 C.1）。
   - **数据末端**：`L` 所在桶通常 `closed = false`，不写；`L` 恰好是桶的最后一分钟时，该桶当轮即可写入。
5. 部分覆盖的桶（桶内有 1m 缺口）**不写**：半截蜡烛的高低点与成交量都是错的，图上留白才诚实（R-7.3）。
   被扣留的桶必须可量化：每周期给出**被扣留桶数**与**合计缺失分钟数**，
   且这些数字必须由 SQL 从 1m 推导，**不得**落一张「扣留表」。
6. 派生层**不新增缺口来源**：高周期的空白是 1m 的 `gaps`（v0.1.0 R-11）与 R-3 判据的投影；
   不允许出现第二套缺口登记。
7. 判据必须实现为可单测的纯函数（输入 `F`/`L` 与桶内行集合 → 是否写入 + 扣留统计），
   并参数化到四个周期与多标的。

### 3.2 派生执行

#### R-4 唯一写入出口与同事务增量

1. 聚合必须挂在 **1m 的唯一写入出口**上。当前写入 1m 的路径有三条
   （`_stream_pull_and_write` 的每批提交、缺口回补的内联 `write_bars`、`run_backfill` 的流式写入），
   必须收敛成**一个**函数（如 `write_bars_and_aggregate`），且以下路径全部经过它：
   增量同步（`data sync` 与守护进程）、缺口自动回补、`data backfill`、`data fetch --source binance`。
   **任何新的 1m 写入路径都必须经过它**——否则聚合会变成「看运气」。
2. 聚合与 1m 写入**同一事务**：该批 1m 落库后，在同一事务内对**桶对齐后的区间**
   （起点 `bucket_start(batch.min, W)`，终点 `batch.max + 60_000` 向上取整到桶边界）重算并 UPSERT
   全部合格桶，然后与水位一起提交。
   - 同事务的理由：不允许存在「1m 已提交、派生没跟上且无人察觉」的窗口；每批一个事务（v0.1.0 R-3.2）
     与「状态与数据同事务」（R-19.5）的语义不变。
   - 按**桶**对齐而不是按批边界重算，保证跨批的桶被完整重算，且同一天内重复重算同一桶是幂等的。
3. **回补必须触发重算**：缺口回补的取值范围同样进入聚合。因此「删掉 1m 中间若干行 → 下一轮自动补回」
   之后，受影响的高周期桶在**同一轮内**出现，不需要人工 `--rebuild`（与 v0.1.0 AC-7 同一精神）。
4. 增量路径**只增不删**：绝不删除已写入的派生桶（1m 历史不可改写，v0.1.0 R-12.3）。
   若 1m 被外部改动导致某桶不再合格，由 R-5 的 `--check` 报出、`--rebuild` 修复。
5. 聚合**不得出网、不得消耗交易所配额、不得新建 Python 子进程**：它是同一进程内的本地 SQL。
6. 聚合失败 → 该批**整批回滚**（连 1m 一起），抛结构化错误码 `AGGREGATION_FAILED`，
   按「需人工介入」处置（进入 `error`，不无限重试）。
   为了故障时能恢复 1m 同步，允许用 `data.aggregateIntervals: []` **显式**关闭派生（R-9.1），
   且关闭状态必须可见（R-8.4 / AC-22）。
7. 派生表写入受既有单标的 advisory lock 保护（v0.1.0 R-3.3），**不得新增并发写路径**。

#### R-5 重建与校验入口（`data aggregate`）

```
trade-tool data aggregate --symbol <SYMBOL>
        [--intervals 15m,1h,4h,1d] [--from <ms>] [--to <ms>]
        [--rebuild] [--check] [--json]
```

1. 语义：
   - **补齐（缺省）**：对区间内全部合格桶计算并 UPSERT，**不删除**任何已有桶；区间缺省 `[F, L]`。
   - **`--rebuild`**：同一区间**先删后算**（删该区间的派生桶再重算），用于修复「1m 被改动 / 派生被篡改」。
   - **`--check`**：只读校验，报出三类不一致——派生表存在但按当前 1m 已不合格（stale）、
     合格但缺失（missing）、值不一致（mismatch）。发现任一不一致 → 抛 `AGGREGATION_MISMATCH`（退出码非 0）。
     与 `data verify` 的分工：verify 重建 1m 的 `verified_upto` 基线，check 只报告派生一致性、不写库。
2. `--intervals` 缺省取 `data.aggregateIntervals`；显式给出时以命令行为准（显式优先于配置）；
   出现本期未实现的周期（`1m` / `5m` / 其它）→ `CONFIG_INVALID`。
3. 必须分批执行（`data.aggregateBatchBars`，keyset 分页），每批一个事务；不得把整段历史一次聚合。
4. 不进交易所、不改 `sync_state` 的水位与 `rows`：只读 1m、只写派生表。
5. **单写者**：必须取与 `SymbolLock` **同一个锁键**
   （`hashtextextended(current_schema() || '/' || exchange || '/' || symbol, 0)`）的 session 级 advisory lock，
   抢不到抛 `SYNC_ALREADY_RUNNING`；但**不得**因此创建 `sync_state` 行——
   库里已有数据、只是没进集合的标的，不能因为跑一次重建就多出一行幽灵状态。
6. 输出（成功时 stdout 是单个 JSON；`--json` 时纯 JSON）：`symbol`、`from` / `to`、
   每周期 `{ upserted, withheldNotClosed, withheldIncomplete, missingMinutes }`、`durationMs`。
   **不许只报「成功」**。
7. 幂等：连续两次补齐，第二次 `upserted = 0` 且派生表逐值不变；`--rebuild` 连续两次结果逐值相同。
8. 失败语义沿用 v0.1.0 R-14：非 0 退出、结构化错误码、stdout 不输出半截 JSON。

### 3.3 读取与控制面

#### R-6 读侧契约

1. `readBars` / `readLatestBars` 增加周期参数，**缺省 `1m`**，既有调用与行为逐字节不变（AC-13）。
2. 周期 → 表名必须经**显式白名单**映射；未知或未实现的周期抛 `CONFIG_INVALID`。
   表名不可参数化，白名单是唯一安全做法，**不得**把周期字符串拼进 SQL。
3. 派生表与 `klines_1m` 共用同一个行映射（`toBar`）与同一组 NULL / NaN 校验，不得为派生表再写一份
   （v0.1.0 R-2.5「不持影子定义」）。
4. 水位（`watermark` / `verified_upto`）语义**只属于 1m**；读侧不得为派生表编造「已同步到哪里」。

### 6.2 实现期修正的判据缺陷（R-3.4）

需求原文的有效窗口是 `win = [max(b, F), min(b + W - 60_000, L)]`。它对 onboard 首日
（附录 C.1）是对的，但有一个未被覆盖的失效：**删掉该标的全局最早的一根 1m 会让 `F`
右移，`expected` 随之减少，桶「自动变回合格」**——而它的值早就是按整桶根数算出来的。
`--check` 此时只会报 `mismatch`，看不出「这个桶本来就不该存在」。

因此实现把判据拆成两条，各司其职：

| 用途                    | 判据                                                                                     |
| ----------------------- | ---------------------------------------------------------------------------------------- |
| **能不能写 / 扣不扣留** | `judge_bucket`：`win` 起点在「桶内最早一根 == F」（onboard）时取 `F`，否则取 `b`         |
| **`--check` 的 stale**  | 派生表里**已有**的桶，若桶内根数不足一个满桶**且**它不是 onboard 前缀桶（桶内首根 != `F`）→ stale |

第二条必须排除前缀桶：onboard 首日那个「合法但不满」的桶正是靠第一条写进去的，
一并报成 stale 会让**每个新标的**的 `--check` 都失败——而 `--check` 的意义恰恰是
「一致时不报」。

**一处无法从数据上区分的残余情形**：「删掉该标的全局最早一根 1m」之后，桶内首根仍然
等于（新的）`F`，与真正的 onboard 前缀桶在数据上完全一样。此时 `--check` 报
**mismatch** 而非 stale —— 值确实对不上（`open` / `volume` 等少了一根的贡献），
由 `--rebuild` 修复。硬要报 stale 就得靠一个「`F` 距 `b` 超过 N 分钟」的距离阈值去赌，
而那在 `onboardDate` 恰好靠近桶边界时会误伤正确的桶。

### 6.3 性能

> **本节的数字是自测的参考值，不承载任何 AC。** 验收里没有任何一条以性能为判据
> （AC-1..22 全部是行为与数据正确性）；这里记录只是为了不让后来者误以为「派生层免费」。

聚合挂在每批写入上，因此它的常数因子直接乘在同步耗时上。实测（30 天 / 43 200 根 1m，
四个周期，每批 500 根，**含事务提交**）：

| 场景                                     | 耗时              |
| ---------------------------------------- | ----------------- |
| 首次全量（桶尚不存在，`before` 为空）    | **211 ms / 批**   |
| 增量（桶已存在，需要整桶齐全 + 写前集合）| **327 ms / 批**   |

**这不是「无感知的开销」**，如实记录：30 天首次全量按 500 根分批约 87 批，即约 18 秒
纯聚合耗时。`sync-integration` 的 AC-2 集成用例（30 天首次全量，真实 Python 引擎 + 真实 PG）
实测 **17.5 s**，改动前（v0.1.0，无派生层）约 **9 s**。

已做的两项优化（各自可复核）：

1. **四个周期共用一次 1m 读取**。四个周期读的是同一批行，逐周期各读一遍等于把最贵的
   查询做四遍。改由 `aggregate_batches` 按最宽周期读一次，各周期在内存里切桶。
2. **`upserted` 不再查「写后桶集合」**。`ON CONFLICT DO UPDATE` 的 rowcount 恒等于
   受影响行数，用它当幂等断言会假失败；改成「实际落库的桶 − 写前已有的桶」后，答案
   已由写入列表与写前集合给出，省掉一次范围查询。

**为什么仍然有量级**：扣留统计与整桶齐全判定需要**全区间**的 `GROUP BY`，而增量场景
比首次全量更贵——桶已存在时 `whole_buckets` 那次查询不能省（首次全量 `before` 为空，
直接跳过）。要继续压就得把扣留统计改成增量维护，但那会引入第二套状态，正是 R-1.5
禁止的。当前开销换来的是「扣留数字永远由 SQL 从 1m 现算、与写库判据同源」。

### 6.3.1 一处已作废的早期数据

实现早期曾用一个**纯内存微基准**测出过一个显著更低的单批耗时，并写进本节。那个基准
跳过了事务提交与 1m 的实际读取路径，**不代表真实链路**——以端到端（真实 Python 引擎 +
真实 PG）的数字为准，即上表的 211 / 327 ms。此处保留这条记录，是为了让后来者知道
早期那个数字错在哪，避免照着它估算容量。

### 6.4 AC-12 与 R-7.1 的一处规格冲突（已按 R-7.1 实现）

两条要求无法同时满足：

| 出处      | 要求                                                |
| --------- | --------------------------------------------------- |
| **R-7.1** | 回包要带上**实际生效**的 `interval` 与 `intervalMs` |
| **AC-12** | 缺省 `?interval` 省略时，**响应与改动前逐字节一致** |

页面要在 4h 图上把缺口算成「缺几根 / 几段 / 最长连续」，就必须知道桶宽；而桶宽写死
在前端就会把 4 小时说成 1 分钟（R-7.3）。所以实现按 **R-7.1** 办：回包多两个字段，
`items` 数组本身与改动前逐字节一致。

这是有意的取舍并在此显式记录，而不是默默偏离：**兼容性上真正会被外部脚本依赖的是
`items` 的内容与顺序**，而 `limit` 字段在 v0.1.0 就已经是回包的一部分、为「如实说明
是否被截断」而存在——再往同一对象上加两个同性质的「生效值」字段不引入新的兼容类别。

### 6.5 其它两处实现取舍

**`upserted` 的定义**：「本轮**新写入**的桶数」，即实际落库的桶减去写前已存在的桶。
不能用 `conn.rowcount`——`ON CONFLICT DO UPDATE` 重复执行时每行都是一次真实 UPDATE，
rowcount 仍等于行数，那会让「第二次 `upserted = 0`」这条幂等断言恒假（AC-7）。

**未启用派生的表示法**：`SyncRunSummary.aggregated` 用 `null` 表示「未启用派生」，
`{}` 表示「启用了但一个桶都没写」。两者在控制面上必须能分开说：前者该去改配置，
后者该去等数据或查缺口。`readDerivedIntervals` 同理返回
`{ withheldReason: 'disabled' }` 而不是全 0（R-8.4 / AC-22）。

build 一并拉进计划：`build test` 合跑是 7 + 7 = 14；单跑 `test` 则是 7 个 `#test` +
被依赖拉进来的 5 个上游 `#build` = 12。

计划数与实际执行数不同，差额来自「有计划、无产出」的任务——`@trade-tool/tsconfig` 没有
build/test 脚本，`@trade-tool/cli` 没有 test 脚本：

| 命令                          | 计划 | 实际执行（`--force`，0 cached） |
| ----------------------------- | ---- | ------------------------------- |
| `turbo run build --force`     | 7    | `6 successful, 6 total`         |
| `turbo run test --force`      | 12   | `9 successful, 9 total`         |
| `turbo run build test --force`| 14   | `11 successful, 11 total`       |

**引用口径**：本节标题与「7 build / 12 test」指的是 `turbo run test --dry=json` 的
**计划**条数。引用执行条数时必须连命令一起写（缓存命中时还会更少）。两者不可混用。
