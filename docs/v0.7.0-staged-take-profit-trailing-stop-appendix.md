## A. 为什么必须换掉 `closePosition`（推导）

### A.1 现有形态

`apps/executor/src/service.ts:267`（`placePair`）挂两张单，都经
`OrderPlacer.placeClosePositionOrder`，其实现在 `packages/data/src/binance-private.ts:484`
硬编码为：

```ts
algoType: 'CONDITIONAL',
type: request.type,        // 'STOP_MARKET' | 'TAKE_PROFIT_MARKET'
triggerPrice: request.stopPrice,
closePosition: 'true',     // ← 固定
```

### A.2 两条因此成立的性质

1. **触发时平掉当时剩余的全部仓位**（不带数量）。
2. **仓位归零时另一张由交易所自动撤销**。仓库把第 2 条当成设计保证写进了
   `apps/executor/README.md`：

   > 仓位平掉后剩余那张由交易所自动撤销——撤销关系在交易所侧，本地不轮询、不盯市，
   > 进程崩了也不会留下裸奔仓位。

### A.3 冲突点

`closePosition=true` 官方明确**不能**与 `quantity`、`reduceOnly` 并存，同时发是 `-1106`
（代码注释 `binance-private.ts:479` 已记录，核对于 2026-10-10）。因此：

- 「条件单只平一半」在 `closePosition` 形态下**不可能**；
- 任何分批止盈都必须换成带 `quantity` 的条件单，于是**主动放弃 A.2 第 2 条**。

主文档 §R-1.1 的选择：**止损保留 `closePosition`（放弃第 2 条的是止盈单，不是止损单）**。
这条选择让减仓之后止损继续有效，因而第一段成交**不需要重挂止损**——
这与最初设想的「第一段成交后要立刻重挂」相比，少了一个无保护窗口。

## B. 为什么止损不用带数量（推导，对应 R-1.1）

设 `q_total` 为建仓量、`q1` 为第一段减仓量。

| 方案                                     | 减仓后剩余 `q_total − q1` 时的行为                                            | 结论            |
| ---------------------------------------- | ----------------------------------------------------------------------------- | --------------- |
| SL `closePosition` + TP1 `quantity`      | SL 仍平**全部剩余**；TP1 只平 `q1`；仓位归零时 SL 自动撤销                    | ✅ **本期采用** |
| SL `quantity = q_total` + TP1 `quantity` | SL 剩余数量 > 剩余仓位 → 触发时**平不掉全部**；无 `reduceOnly` 时可能反向开仓 | ❌ 危险         |
| 两张都 `quantity`                        | 与上一行同型，只是把风险分散在两张单上                                        | ❌              |
| 两张都 `closePosition`                   | 无法减仓                                                                      | ❌ 无法实现分批 |

「短暂双挂两张 `closePosition` 单」的安全性依据：`closePosition` 的语义是**只平不开**，
因此重叠期内即使两张都被触发，最坏结果是第二次得到「无仓可平」的拒绝，
**不会开出反向仓位**。这条是 R-4.2 的前提，**同样属于待核实项**（§E.4）。

## C. 迁移草案 `packages/data/sql/010_risk_trailing.sql`

> 草案，不是最终稿。最终稿必须在实现时补上与 `006` 相同的头注释（存在的理由 + 幂等要求 + 约定沿用）。

```sql
-- 010_risk_trailing：v0.7.0 两段止盈 + 移动止损的阶段与档位。
--
-- 存在的理由：risk_bracket 的 state 原本只有五个值，装不下「第一段已成交、
-- 剩余仓位在移动止损中」这个中间阶段；而移动止损需要记住**持仓期极值**与
-- **当前生效的档位**，否则进程重启即丢档，等于移动止损在重启后失效。
--
-- 刻意**没有** stage 列：阶段由 state 表达。再加一列阶段就是第二套状态。
--
-- 约定沿用既有（R-1）：
--   * 时间戳一律 bigint（epoch 毫秒），不用 timestamptz；
--   * 本文件必须可重复执行（幂等）；
--   * 表结构的唯一来源就是本文件，TS 与 Python 都不得另持影子定义。

-- ---------------------------------------------- risk_bracket：两段与档位
ALTER TABLE risk_bracket
    -- 第一段止盈（带数量的条件单）。takeProfit1Ratio = 0 时这五列恒为 NULL。
    ADD COLUMN IF NOT EXISTS tp1_algo_id     bigint,
    ADD COLUMN IF NOT EXISTS tp1_qty         double precision,
    ADD COLUMN IF NOT EXISTS tp1_price       double precision,
    ADD COLUMN IF NOT EXISTS tp1_filled_qty  double precision,
    ADD COLUMN IF NOT EXISTS tp1_filled_at   bigint,
    -- 移动止损的当前状态。NULL 语义是「未进入 trailing 阶段」，
    -- 与 quote_volume / trades 的「交易所未提供」不是一回事（AGENTS.md §5 第 2 条）。
    -- atr / stop_price / take_profit 三列**保持入场时的值不变**（R-5.3），
    -- 它们记的是「第一段为什么这么算」；移动中的那一档写在 trail_stop_price。
    ADD COLUMN IF NOT EXISTS trail_extreme     double precision,
    ADD COLUMN IF NOT EXISTS trail_stop_price  double precision,
    ADD COLUMN IF NOT EXISTS trail_atr         double precision,
    ADD COLUMN IF NOT EXISTS trail_atr_from    bigint,
    ADD COLUMN IF NOT EXISTS trail_atr_to      bigint,
    ADD COLUMN IF NOT EXISTS trail_updated_at  bigint,
    -- 本轮没有移动的原因。**常驻可见**：极值取不到、越过现价、撤旧失败
    -- 都写在这里，而不是只打一行日志就过去（AGENTS.md 约定 9）。
    ADD COLUMN IF NOT EXISTS trail_last_error  text;

-- state 追加两个值，既有五个值语义不变。先 DROP 再 ADD 的组合重复执行仍幂等。
ALTER TABLE risk_bracket DROP CONSTRAINT IF EXISTS risk_bracket_state_check;
ALTER TABLE risk_bracket ADD CONSTRAINT risk_bracket_state_check CHECK (
    state IN ('armed', 'partial_armed', 'trailing',
              'take_profit', 'stop_loss', 'cancelled', 'failed')
);

-- partial_armed 必须有第一段的量与价；trailing 必须有当前档位。
-- 钉在 schema 里而不是靠应用层自觉：漏写的那一行会让「账面在移动、
-- 实际上没有档位」安静地存在。
ALTER TABLE risk_bracket DROP CONSTRAINT IF EXISTS risk_bracket_staged_check;
ALTER TABLE risk_bracket ADD CONSTRAINT risk_bracket_staged_check CHECK (
    (state = 'partial_armed'
        AND tp1_algo_id IS NOT NULL AND tp1_qty IS NOT NULL AND tp1_price IS NOT NULL)
    AND (state <> 'trailing'
        OR (trail_stop_price IS NOT NULL AND trail_stop_price > 0))

-- 数量必须落在 (0, 持仓量] 之内：0 或超过持仓量都意味着这张单挂出来就是错的。
ALTER TABLE risk_bracket DROP CONSTRAINT IF EXISTS risk_bracket_tp1_qty_check;
ALTER TABLE risk_bracket ADD CONSTRAINT risk_bracket_tp1_qty_check CHECK (
    tp1_qty IS NULL OR (tp1_qty > 0 AND tp1_qty <= filled_qty)
);

-- ---------------------------------------------- risk_policy：两段与追踪的参数
-- 取值范围照抄 executorSchema（AGENTS.md §6.4 第 4 条）。
-- DEFAULT 必须与 executorSchema 的缺省**逐字相同**（R-11.3）。
ALTER TABLE risk_policy
    -- 0 = 关闭分批，行为与 v0.4.0 一致。
    ADD COLUMN IF NOT EXISTS take_profit1_ratio     double precision NOT NULL DEFAULT 0,
    ADD COLUMN IF NOT EXISTS take_profit1_atr_mult  double precision NOT NULL DEFAULT 3,
    ADD COLUMN IF NOT EXISTS trail_atr_mult          double precision NOT NULL DEFAULT 2,
    ADD COLUMN IF NOT EXISTS breakeven_after_tp1     boolean          NOT NULL DEFAULT true;

ALTER TABLE risk_policy DROP CONSTRAINT IF EXISTS risk_policy_tp1_ratio_check;
ALTER TABLE risk_policy ADD CONSTRAINT risk_policy_tp1_ratio_check
    CHECK (take_profit1_ratio >= 0 AND take_profit1_ratio < 1);

ALTER TABLE risk_policy DROP CONSTRAINT IF EXISTS risk_policy_tp1_mult_check;
ALTER TABLE risk_policy ADD CONSTRAINT risk_policy_tp1_mult_check
    CHECK (take_profit1_atr_mult > 0 AND take_profit1_atr_mult <= 50);

ALTER TABLE risk_policy DROP CONSTRAINT IF EXISTS risk_policy_trail_mult_check;
ALTER TABLE risk_policy ADD CONSTRAINT risk_policy_trail_mult_check
    CHECK (trail_atr_mult > 0 AND trail_atr_mult <= 20);
```

## D. 限频与容量估算

一轮移动止损定时器（`trailIntervalMs = 60_000`）对**每条** `trailing` 记录：

| 动作                 | 出网？ | 权重                                                    |
| -------------------- | ------ | ------------------------------------------------------- |
| `risk-atr`（含极值） | **否** | 0——它只读本地 PG（`quant_data.risk` 从 `klines_1m` 读） |
| 撤旧止损             | 是     | 按撤单权重 1 估                                         |
| 挂新止损             | 是     | 按下单权重 1 估                                         |

按「价未变就不动」（R-3.2）的口径，正常行情下每轮真正动的手是**零到少数几条**。
把 60 秒一轮、20 条同时 `trailing` 全都变了的最坏情况算一遍：40 次请求/分钟，
10 秒窗口内约 7 次——相对 `X-MBX-ORDER-COUNT-10S` 的量级可以忽略。

⚠️ **这些权重是估算，不是核对过的常量**。真正要用的数字只有两个来源：
`packages/data/src/binance-private.ts` 里已有的注释（`openAlgoOrders` 无 symbol 权重 40、
带 symbol 权重 1；`positionRisk` v3 权重 5）与官方 rate-limit 表。实现时把两边对上，
**不要把本表的算式当成会自我校验的事实**（AGENTS.md §6.5 里对「45」那段就是这么处理的）。

### E.3 ✅ **已核对**（2026-10-17）：`reduceOnly` 是**支持的**参数（单向持仓下）

官方参数表把 `reduceOnly` 列为 Algo 条件单的合法参数。本仓库用**单向持仓**（§6.3 第 7 条已直接拒绝
双边模式），因此它在带数量的第一段止盈单上**可用**——官方明确的「Cannot be sent in Hedge Mode」
这条限制对本仓库不构成障碍。

这推翻了本附录此前采信的第三方报告：

| 来源                                             | 说法                                                            |
| ------------------------------------------------ | --------------------------------------------------------------- |
| nautilus_trader issue #4192（用户报告，2026-06） | Algo API **不支持** `reduceOnly`，发了返回 `-1106`              |
| 同 issue 下的维护者修复提交（2026-06）           | 描述里提到「单向模式 reduce-only 仍发送它」——暗示**支持**       |
| **官方参数表（2026-10-17 直连）**                | `reduceOnly` 是合法参数，仅禁用于 Hedge Mode 与 `closePosition` |

**处置**（据此改主文档 N-1）：`reduceOnly` 从「明确不用」改为「**默认带上**」——
它给带数量的减仓单加一道「只减不开」的保险，成本为零。若 demo 实测报错，去掉即可；
设计**不依赖**它——第一段止盈的语义靠 `quantity` 本身成立。

### E.4 **待核实**：两张 `closePosition` 单重叠时的行为

R-4.2（先挂新、再撤旧）依赖「重叠期内第二张触发只得到『无仓可平』的拒绝，**不会反向开仓**」。
依据是 `closePosition` 的官方语义（只平不开），但**实测数据没有**。

demo 上验证：同一标的一张 `closePosition` 止损挂两张不同触发价，
手动平掉仓位后触发价更近的那张，看它是「被拒」「被自动撤销」还是「被正常忽略」。
结果决定 R-4.2 要不要补一句兜底（例如撤旧失败时改回「先撤后挂」并记 `trail_last_error`）。

### E.5 头号回归点：`settle()` 会抹掉 `trailing`

现有 `apps/executor/src/service.ts:193`：

```ts
await markBracketSettled(pool, key, tag === TP_TAG ? 'take_profit' : 'stop_loss', now());
```

`markBracketSettled`（`packages/data/src/db/risk.ts:249`）是**无条件** `UPDATE … SET state = $4`。
第一段止盈成交走的就是这条路径 → 它会把刚置好的 `trailing` **覆盖成终态 `take_profit`**，
于是移动止损永远不会被启动，而账面上显示「这笔交易已经了结」。

改造要求（R-8.1）：`settle()` 必须先读当前 `state`，
`trailing` / 已终结的行**直接返回幂等结论**，不做 UPDATE。
这条要有专门用例，且用例必须断言**TP1 成交后 state 仍为 `trailing`**——
只断言「返回了 settled」会漏掉这个覆盖。

### E.6 `parseStepSize` 的数据来源

`contract_spec.raw` 是 `exchangeInfo` 的整段 JSONB，`LOT_SIZE` 在
`symbols[].filters[]` 里按 `filterType = 'LOT_SIZE'` 定位。现有 `parseTickSize` 已经在做同一件事

`q1 × price` 低于它时挂单会被拒——按 N-8 **不自动兜底**，直接留可见失败记录。

## F. 剩余仓位的两条路线对比（**已决策：走路线 A**）

> **决策记录（2026-10-17，用户）**：选**路线 A（自建 Chandelier）**。
> 理由是止损距离要**随行情波动自适应**——这是路线 B 给不了的。
> 代价（定时器、档位落库、重启恢复、每次挪单的空档）由本设计逐条兜住，见主文档 R-3 / R-4 / R-5。
> 路线 B 不是错的，只是不满足「距离跟着波动走」这一条；它记在这里是为了**别让下一个人重新发现一遍再问一遍**。

2026-10-17 的官方核对里有一条此前完全没进视野的能力：**原生 `TRAILING_STOP_MARKET`**。

官方参数表与 Notes 原文：

- `type` 对 `CONDITIONAL` 支持
  `STOP_MARKET`/`TAKE_PROFIT_MARKET`/`STOP`/`TAKE_PROFIT`/**`TRAILING_STOP_MARKET`**
- `activatePrice` — Used with `TRAILING_STOP_MARKET` orders, default as the latest price
- `callbackRate` — Used with `TRAILING_STOP_MARKET` orders, **min 0.1, max 10 where 1 for 1%**
- 触发口径（Notes 原文）：
  `BUY`: the lowest price after order placed <= `activatePrice`, and
  the latest price >= the lowest price * (1 + `callbackRate`)；
  `SELL` 完全镜像。

**关键点：它追踪的口径是「下单之后的最低 / 最高价」——与 Chandelier 的「持仓期极值」是同一个定义。**

| 维度            | 路线 A：自建 Chandelier（当前文档）      | 路线 B：原生 `TRAILING_STOP_MARKET`                        |
| --------------- | ---------------------------------------- | ---------------------------------------------------------- |
| 追踪基准        | 库内 1m 的持仓期极值（自算）             | 交易所维护的极值                                           |
| 距离            | `k × ATR(最新)`，**随波动率自适应**      | `callbackRate` 固定百分比（0.1%–10%）                      |
| 剩余仓位怎么挂  | `closePosition` 止损，按档位**撤旧挂新** | `closePosition`，**一次挂好，永不重挂**                    |
| 本地需要的机制  | 定时器 + 档位落库 + 重启恢复 + 重挂时序  | **无**（除了第一段成交的幂等）                             |
| 无保护窗口      | 有，靠「先挂后撤」压到最短（E.4 待核实） | **没有**（交易所侧不存在重挂）                             |
| 进程崩了        | 停在旧档，重启后靠定时器续做             | **照常工作**                                               |
| 吃交易所权重    | 每档 1 挂 + 1 撤                         | **0**                                                      |
| 「ATR」这个诉求 | 真 ATR，波动率变化时距离跟着变           | 挂单那一刻把 `k×ATR/price` 折算成 `callbackRate`，之后固定 |

**路线 B 用 `closePosition` 挂剩余仓位，第一段成交导致仓位减半时它同样继续有效**——
与路线 A 的止损单一样，减仓不需要重挂。

### F.1 路线 B 的连带成本（都是可验证的具体改动）

1. **`algoOrderTag` 会抛错**。`packages/core/src/risk-ids.ts:65` 只认
   `TAKE_PROFIT*` 与 `STOP*`，`TRAILING_STOP_MARKET` 两个前缀都不匹配 →
   `throw SyncError('EXCHANGE_ERROR', '无法识别的条件单类型')`。它是对账解析条件单类型的入口，
   走路线 B 就必须补这一类（注意 §6.3 已有的结论：查询侧与下单侧的 `orderType` 取值**必须原样透传**，
   不许在解析层「顺手统一」）。
2. **它止损、不是止盈**。原生追踪单在**回撤**方向触发，只保护已有的浮盈；
   它**不会**像「追踪止盈」那样在上涨途中主动了结。因此路线 B 的语义是
   「第一段兑现 + 剩余仓位交给追踪止损」，而不是「剩余仓位主动止盈」。
3. **`activatePrice` 有方向约束**（Notes 里给了 `-2021 Order would immediately trigger` 的条件：
   BUY 时 `activatePrice` 要小于现价）。它与路线 A 的 R-7「越过现价就不挂」是同一条纪律的两种实现。
4. **回调率是百分比**，最小 0.1%。极小波动或极小 ATR 折算出来可能落在下界之外，
   按 §5 第 8 条**显式报错**，不许夹逼到 0.1%。

### F.2 决策建议

- 要**真·ATR 自适应**（波动放大时保护距离跟着拉开）→ 路线 A。
- 要**先把功能落地、风险面小、进程崩了也不失效** → 路线 B，并在页面上把 `callbackRate`
  做成可填字段（挂单时按 `k×ATR/price` 自动折算成一个初值，允许人工覆盖）。
- 两条路线**共享**全部已定的第一段逻辑（`quantity` 止盈、`reduceOnly`、状态机 `partial_armed`、
  `settle()` 幂等改造、比例参数化）。**第一段不因选哪条而改变**，因此这不是二选一的重做，
  而是「`trailing` 阶段之后那部分」的取舍。

## H. 比例参数化的增量成本（`takeProfit1Ratio` 从 50% 泛化到任意百分比）

用户要求比例**在页面上可设**（如 80% / 100%），因此取值范围从「固定 0.5」改成 `0 ≤ ratio ≤ 1`。
逐层核对下来，**比例泛化本身几乎不增加难度**：

| 层                             | 改动                                                                              | 量级 |
| ------------------------------ | --------------------------------------------------------------------------------- | ---- |
| `packages/core` 纯函数         | `q1 = alignToQty(filledQty × ratio, stepSize, 'down')`；校验 `0 < q1 < filledQty` | 小   |
| `executorSchema`               | 取值范围 `0 ≤ ratio ≤ 1`（原为 `0 ≤ ratio < 1`）                                  | 小   |
| `risk_policy` CHECK            | `take_profit1_ratio >= 0 AND take_profit1_ratio <= 1`                             | 小   |
| `resolvePolicy`                | **无需新增合并规则**——比例没有「别名参数」                                        | 无   |
| `RiskPolicyPanel.tsx`          | 加 1 个数字输入（0–100 的百分数 ↔ 0–1 的小数换算）+ 范围校验 + 提示               | 小   |
| `packages/data/src/db/risk.ts` | `tp1_qty` 的 CHECK 已写成 `0 < q1 <= filled_qty`（C 节草案），无需改              | 无   |

**80% 与 100% 的实现成本完全相同**，因为它们走同一条路径、同一个状态机。
唯一需要新增的分支是 `ratio = 1`：

| 取值            | 语义                           | 下单形态                                | 剩余仓位 |
| --------------- | ------------------------------ | --------------------------------------- | -------- |
| `ratio = 0`     | 关闭分批（v0.4.0 行为）        | TP `closePosition` + SL `closePosition` | 无       |
| `0 < ratio < 1` | 第一段减仓 ratio，剩余交给追踪 | TP1 `quantity` + SL `closePosition`     | 追踪中   |
| `ratio = 1`     | 第一段**全平**，等价一次性止盈 | TP1 **退化为 `closePosition`**          | **无**   |

`ratio = 1` 的处理是本期设计里最省的一处：**它直接退回 v0.4.0 的形态**——
止盈单重新带上 `closePosition=true`，交易所自动撤单的保证一分不丢，不进 `trailing`，
因此也不需要移动止损与定时器。换句话说「100%」比「80%」**更简单**。

⚠️ 页面上的百分比换算必须**单点实现**（一个 `percentToRatio` / `ratioToPercent`），
不能在前端输入框里 `÷ 100` 之后再让后端与 DB 各存一份口径（§6.4 第 4 条治的正是这个）。
