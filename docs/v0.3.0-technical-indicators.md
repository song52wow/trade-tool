## 1. 背景

v0.1.0 把 1m 拉全并固化进 `klines_1m`；v0.2.0 由它派生出 15m / 1h / 4h / 1d，并立下一条规矩：
**高周期只由库内 1m 派生，不向交易所取**（v0.2.0 §1）。本期沿这条线再走一层：**指标只由库内已收盘的 K 线派生。**

本期要解决的三件事，按重要性排序：

1. **指标实现正在分裂**。`sma` 现在有两份：`packages/core/src/strategy.ts` 的 TS 版与
   `python/.../quant_core/indicators.py` 的 Python 版，分别被两套回测引擎使用。AGENTS.md 明令
   「不得持影子定义」，但这份重复已经存在。**再加 7 个指标就会变成 7 对重复**——而两侧只要差一次
   浮点舍入，同一根 K 线上的同一个买点就会分叉，症状是「回测赚钱、实盘不赚」且几乎无法定位。
   因此本期**先把实现收敛到一处**（R-1 / R-7），再谈功能。
2. **下一步需求是「用指标自动判断买入点」**。买点的成败八成不在指标算得准不准，而在**可用时刻**
   （look-ahead）。现有回测模型「看到本根收盘价、又以本根收盘价成交」是不能拿来做买点的（R-2 / R-8）。
   这条契约现在写进文档是零成本，等买点做完再回头改数据层就是全链路返工。
3. **看图要能看到指标**。控制面是 TS，读路径必须是**纯读 PG、不出网、不 spawn 子进程**
   （v0.1.0 R-23.4 / R-17.6）。所以图上的指标**只能来自物化表**——这是物化不可省略的真正理由，
   而不是「算得慢」。

第 3 条同时定下了物化与现算的分工，这也是「参数改了能不能适配」这个问题的答案：

| 消费方          | 需求                           | 走哪条                                                |
| --------------- | ------------------------------ | ----------------------------------------------------- |
| 回测 / 参数扫描 | 全历史、成百上千组参数组合     | **现算**（`quant_core` 纯函数）——物化表装不下参数组合 |
| 看盘 / Web 图表 | 固定参数集、最近若干根、低延迟 | **物化**（TS 侧纯读）                                 |

**计算是唯一真相且对任意参数都能算；物化只是「已定稿参数集」的读时缓存。** 参数变更之所以能适配，
靠的是计算函数不依赖表，而不是表设计得巧（R-3.6）。

## 3. 需求条目

### 3.1 指标计算（唯一实现）

#### R-1 口径与唯一实现

1. 7 组指标的**唯一实现**放在 `quant_core`。TS 侧（`packages/*`、`apps/*`）**不得出现任何指标实现**：
   既有 `packages/core/src/strategy.ts` 的 `sma` / `lastDefined` 必须删除（AC-16 用 `grep` 守住）。
2. 全部指标是**纯函数**：输入等长的 OHLCV numpy 数组，输出等长数组；不读时钟、不做 IO、不用随机数。
   与 AGENTS.md 硬性约定 4（策略无状态、`onBar` 必须是纯函数）同一条规则。
3. 口径逐条钉死（推导与边界见附录 A）。`EMPTY` 表示预热不足、该位置不产生行：

   | 指标 | 参数（全为整数）                 | 有效起点（段内 0-based） | 关键口径                                                                                  |
   | ---- | -------------------------------- | ------------------------ | ----------------------------------------------------------------------------------------- |
   | SMA  | `window` W                       | `W-1`                    | 收盘价算术均值                                                                            |
   | EMA  | `span` S                         | `S-1`                    | `alpha = 2/(S+1)`；**种子 = 段首 `S` 根的算术均值（SMA 播种）**，`i ≥ S` 起递推           |
   | MACD | `fast` F / `slow` S / `signal` G | `S+G-2`                  | `DIF = EMA(F) − EMA(S)`；`DEA = EMA(DIF, G)`；**`HIST = DIF − DEA`**（见下）              |
   | RSI  | `period` N                       | `N`                      | Wilder 平滑；首个 `avgGain/avgLoss = mean(gain[1..N]) / mean(loss[1..N])`                 |
   | BOLL | `period` P / `k_milli`           | `P-1`                    | `MID = SMA(P)`；**`STD` 用总体标准差（÷P，不是 ÷(P−1)）**；`k = k_milli/1000`             |
   | KDJ  | `n` / `k_period` / `d_period`    | `n-1`                    | `RSV`；`K_i = (kp−1)/kp·K_{i-1} + 1/kp·RSV_i`；`D` 同式；`J = 3K − 2D`；`K/D` 初值 **50** |
   | ATR  | `period` N                       | `N`                      | Wilder；`TR_0 = high_0 − low_0`；`ATR_N = mean(TR[1..N])`                                 |
   | OBV  | 无                               | `0`                      | `OBV_0 = 0`；收涨 `+vol`、收跌 `−vol`、持平不变                                           |

4. **参数一律是非负整数**，因此可以进主键且没有浮点相等问题（R-3.2）。凡口径上需要小数的参数一律
   存为千分之一整数（`k_milli = 2000` 表示 `k = 2.0`）。**不得**把浮点参数写进主键。
5. **两处必须显式择一、不得含糊的口径**（写进代码注释与 AC）：
   - **MACD 柱**：本期取 `HIST = DIF − DEA`（国际惯例）。国内软件（通达信 / 同花顺）柱值为
     `2×(DIF−DEA)`，**本期不采用**；读侧如需国内口径自行 ×2。两种口径都在用，必须选一种并写明，
     让读侧「自己乘 2」比让库里存一个说不清来源的数诚实。
   - **KDJ 分母为 0**：窗口内 `max(high) == min(low)`（横盘）时 `RSV` 分母为 0，**取 `RSV = 50`**
     （0–100 标度的中性点）。禁止产生 `NaN` / `Inf`，也禁止沿用前值（沿用会让横盘期读成趋势延续）。
6. **OBV 的语义限制必须写进契约**：OBV 是从段首 0 起累加的绝对量，**只有相对变化有意义**；
   段首一变（补了更早的数据），该段全部 OBV 值整体平移。读侧不得把 OBV 的绝对值当作可比量。
7. **EMA 播种口径是对既有实现的有意变更**：现 `quant_core.ema` 以 `values[0]` 起递推，
   而 `(1−α)^(S−1)` 在 `S = 12/26/60` 时分别是 `15.8% / 14.6% / 13.5%`——也就是说「预热 S−1 根」
   并不能让段首种子收敛掉，它只是衰减到 `e^-2` 就停了。改为 **SMA 播种**后，首个输出就是那 `S` 根的
   算术均值，不再是一个说不清来源的数（推导见附录 A.2）。既有单测 `test_ema_starts_at_first_value`
   随本次变更更新，并记入实现记录。

#### R-2 可用时刻（面向买点的硬规范）

本节是**成文契约**，不是实现细节。将来的买点判断必须建立在这条之上。

1. 指标的输入**只能是已收盘的 bar**。这条由 v0.2.0 R-3 保证：派生表在任一时刻只含已收盘且 1m 全覆盖的桶。
   指标层因此**不需要自己的收盘判据**——它继承上一层的，**不得**另立一套（避免 v0.2.0 R-3 那种判据漂移）。
2. **bar `t` 的指标值，语义是「在 `t` 收盘后才可用」。** 禁止在任何决策中使用 `t+1` 及以后的 bar。
3. 回测成交模型固定为：**信号在 `t` 收盘确认，成交在 `t+1` 开盘**。
   - 序列最后一根产生的信号**无法成交**，因此不产生交易；
     **不得**回退成「以 `t` 收盘价成交」——那正是要修掉的未来函数。
   - 涨跌停 / 缺 `t+1` 开盘价的情形：`t+1` 不存在（序列到 `t` 为止）则不成交；
     `t+1` 存在但开盘价缺失属数据损坏，按 v0.1.0 R-4 报错，不静默跳过。
4. 读侧返回的指标序列，其**时间范围必然比 K 线短**（少的正是预热期与未收盘的最后一根）。
   控制面必须把这件事**说在图外**，不能让它看起来像缺数据（R-10.4）。

### 3.2 物化存储

#### R-3 schema 与迁移

1. 新增 `packages/data/sql/005_indicators.sql`：**幂等、可重复执行、空库可一路迁到最新**；
   迁移文件仍是 schema 的唯一来源（v0.1.0 R-2.5 / AC-25）。
2. **7 张指标表，每张表的「参数」是有类型的列并进主键**。`interval` 是列（不是表名），受白名单 + `CHECK` 约束：

   ```sql
   indicator_ma   (symbol, interval, impl_version, kind, window, time, value)
                     kind ∈ {'sma','ema'}；PK(symbol, interval, impl_version, kind, window, time)
   indicator_macd (symbol, interval, impl_version, fast, slow, signal, time, dif, dea, hist)
   indicator_rsi  (symbol, interval, impl_version, period, time, value)
   indicator_boll (symbol, interval, impl_version, period, k_milli, time, upper, mid, lower)
   indicator_kdj  (symbol, interval, impl_version, n, k_period, d_period, time, k, d, j)
   indicator_atr  (symbol, interval, impl_version, period, time, value)
   indicator_obv  (symbol, interval, impl_version, time, value)
   ```

   - 所有参数列与 `impl_version` 都是 `integer NOT NULL` 且有 `> 0` 的 `CHECK`
     （`k_milli` 允许 `>= 0`）。
   - `time` 是 **bar 起点**（epoch 毫秒，`bigint`），口径与派生表一致。
   - `interval` 一律 `text NOT NULL` + `CHECK (interval IN ('15m','1h','4h','1d'))`，
     与 `INTERVAL_TABLES` 的派生周期集合一致，**1m 不在其中**（N-2）。
   - 值列 `double precision`；`symbol` / `time` / 值列均 `NOT NULL`。

3. **参数是数据，不是 schema**：
   - 改 `window` 5→30、加一组 `MACD(8,17,9)`：**插新行，零 DDL**（AC-3）。
   - **不得**出现 `ma_20 double precision` 这类「把参数写进列名」的形态，
     也**不得**用不透明的 `params_hash` 代替可查的参数列——`params_hash` 会让 SQL 查不了
     「所有 `window = 20` 的均线」，还会引入一条跨语言 hash 一致性契约（浮点格式化分歧即静默分叉）。
   - **不得**另持一份「指标 → 表名 / 列名」的影子定义：表名与列集合由迁移文件唯一定义，
     `quant_data` 与 `packages/data` 两侧各引用一次，三方一致性由 AC-2 的测试守住。
4. **`impl_version` 进主键**，初值 `1`，定义在 `quant_core`（`INDICATOR_IMPL_VERSION`）。
   - `params_hash` 式的参数身份只能覆盖「参数」，覆盖不了「实现改了」（例如修了 MACD 的递推 bug）。
     将来要**复现一个历史买点**，光有参数不够。
   - 实现行为变更（口径修改、修 bug）必须**递增**该常量；纯重构、无语义变更不递增。
5. 指标表**没有水位列、也没有状态表**：物化到哪由 K 线数据与 R-4 判据推导。
   新增第二套「同步到哪里」正是 v0.1.0 R-9.6 要避免的。
6. **不落「参数集登记表」**：要物化哪些参数集是**配置**（R-12.1），库里有什么由指标表本身推导。
   这与 v0.2.0 拒绝「扣留表」是同一条理由——状态只能有一处真相。

#### R-4 物化判据与递增（核心）

1. **连续段**：对某 `(symbol, interval, 参数集)`，把该周期的派生行按 `time` 升序排列，
   `time[i] − time[i−1] != intervalMs` 处断开，得到若干**极大连续段**。
2. **每个连续段独立重算，段间不递推**。即段首的递推初值只依赖该段自身，**不得**从上一段的状态接续。
   理由（必须写进代码注释）：若跨缺口递推，则「回补一个久远的 1m 缺口」会把此后**全部**指标值
   静默改掉，而用户从界面上看不出任何解释。v0.1.0 R-11.10「缺口不得插值」的同一精神是
   **缺口就是噪声，不得跨越**。副产品是增量成本从 O(全历史) 降到 O(所在段)。
3. **预热期不落库**：段内位置早于 R-1.3 有效起点的行**不写**。
   - 不写 `NaN`、不写 `NULL`、更不写 `0` 冒充——v0.1.0 R-4.3 明确禁止用 `0` 冒充缺失。
   - 段长度不足以越过预热期时，该段**一行都不写**（记 `withheldWarmup`）。
   - 因此指标表里**每一行都是有效值**，读侧不必做 NaN 分支。
4. **重算起点**：本批聚合在周期 `I` 上触及的桶区间的起点 `b0`（v0.2.0 R-4.2 已算出该区间）。
   - 该周期本批**没有任何桶变化** → 该周期不重算（记 `skipped: 'noChange'`）。
   - 重算区间为 `[所在段起点, 段末端]`（递推初值必须从段首重新推，见 R-4.2），
     但**只 UPSERT `[max(b0, 段首 + 预热期), 段末端]` 的行**。
   - 值未变时不产生新行（`UPSERT ... WHERE 值不同` 或先比后写），保证幂等。
5. 计算**必须向量化**：每个 `(symbol, interval)` 一次性读入全部需要的列，在内存里算全部参数集的
   全部指标。禁止逐 bar Python 循环、禁止逐参数集重复打 PG（O(n²) 是 v0.3.0 要修掉的两个问题之一，R-8.3）。
6. **`impl_version` 不得混版**：增量路径发现该 `(symbol, interval, 参数集)` 已物化的最大
   `impl_version` ≠ 当前 `INDICATOR_IMPL_VERSION` 时，**拒绝写入**并抛 `INDICATOR_IMPL_STALE`
   （需人工介入），提示跑 `data indicators --rebuild`。
   「前半段是 v1 行、后半段是 v2 行」是最坏的结果——它**看起来完全正常**。

### 3.3 派生执行

#### R-5 唯一写入出口与同事务

1. 指标物化必须挂在 v0.2.0 的**同一写入出口** `write_bars_and_aggregate` 上，顺序为
   **写 1m → 聚合派生桶 → 物化指标 → 提交**，**同一事务**。
   - 指标依赖刚写入的派生桶，因此必须在聚合之后；同事务的理由与 v0.2.0 R-4.2 一致：
     不允许存在「K 线已提交、指标没跟上且无人察觉」的窗口。
   - 任何新的 1m 写入路径都必须经过它（v0.2.0 R-4.1 继续成立）。
2. 四条路径（增量同步、缺口自动回补、`data backfill`、`data fetch --source binance`）
   **全部**触发指标物化，由 AC-6 分别断言。
3. 指标物化**不出网、不消耗交易所配额、不新建 Python 子进程**：它是同一进程内的本地计算 + 本地 SQL。
4. 指标物化失败 → 该批**整批回滚**（连 1m 与派生桶一起），抛 `INDICATOR_FAILED`，
   按「需人工介入」处置（进 `error`，不无限重试），与 v0.2.0 R-4.6 同规则。
   为故障时能恢复 K 线同步，允许用 `data.indicatorSpecs` 显式清空来关闭指标层（R-12.2），
   且关闭状态必须可见（R-11.4 / AC-22）。
5. 指标表写入受既有**单标的 advisory lock** 保护（v0.1.0 R-3.3），**不得新增并发写路径**。

#### R-6 重建与校验入口（`data indicators`）

```
trade-tool data indicators --symbol <SYMBOL>
        [--intervals 15m,1h,4h,1d] [--from <ms>] [--to <ms>]
        [--rebuild] [--check] [--json]
```

1. 语义（与 v0.2.0 R-5.1 同形，便于记忆）：
   - **补齐（缺省）**：对区间内全部合格行计算并 UPSERT，不删除任何已有行；区间缺省取该标的数据范围。
   - **`--rebuild`**：同一区间**先删后算**，用于修复「K 线被改动 / 指标被篡改 / `impl_version` 已递增」。
   - **`--check`**：**只读**校验，报出三类不一致——存在但按当前 K 线与当前实现已不可复现（`stale`）、
     应存在但缺失（`missing`）、值不一致（`mismatch`），以及**混版**（同一参数集出现多个 `impl_version`）。
     发现任一不一致 → 抛 `INDICATOR_MISMATCH`（退出码非 0）。
2. `--intervals` 缺省取 `data.indicatorIntervals`；显式给出时以命令行为准（显式优先于配置）。
   出现 `1m` / `5m` / 其它 → `CONFIG_INVALID`，**不得**静默忽略或回落。
3. 必须分批执行（`data.indicatorBatchBars`），每批一个事务；不得把整段历史一次写入。
4. 不进交易所、不改 `sync_state` 的水位与 `rows`：只读 K 线、只写指标表。
5. **单写者**：必须取与 `SymbolLock` 同一个锁键的 session 级 advisory lock，抢不到抛
   `SYNC_ALREADY_RUNNING`；但**不得**因此创建 `sync_state` 行（v0.2.0 R-5.5 继续成立）。
6. 输出（成功时 stdout 是单个 JSON；`--json` 时纯 JSON）：`symbol`、`from` / `to`、
   每周期每参数集 `{ indicator, params, upserted, withheldWarmup, skipped }`、`implVersion`、`durationMs`。
   **不许只报「成功」**。
7. 幂等：连续两次补齐，第二次 `upserted = 0` 且指标表逐值不变；`--rebuild` 连续两次结果逐值相同。
8. 失败语义沿用 v0.1.0 R-14：非 0 退出、结构化错误码、stdout 不输出半截 JSON。

#### R-8 未来函数与复杂度修正

1. **修掉未来函数**：`packages/backtest/src/engine.ts:53-56` 现在是「`onBar` 看到本根收盘价、
   成交也用本根收盘价」。改为 R-2.3：信号在 `t` 收盘确认、**成交在 `t+1` 开盘**；
   序列末根信号不成交。Python 引擎同样遵守。
2. **策略只消费指标，不再自己算指标**：Python 回测从 `quant_core` 取指标序列，禁止在引擎内写
   任何指标公式（AC-16 守住）。
3. **修掉 O(n²)**：现有 `ma-cross` 每根 bar 都把整段历史重算一遍 `sma`（`ma-cross.ts:35-38`），
   在 500 根合成数据上看不出来，对着库内 651 万根 1m 就是不可用。指标一律**向量化一次算完整段**，
   回测主循环 O(n)。
4. 绩效指标（`metrics`）口径**不变**：本次只改成交时点与计算复杂度，不改夏普 / 回撤 / 盈亏比的定义。

### 6.2 规格之外做出的三个判断

1. **`window` → `bars`（订正规格）**。规格写的 `indicator_ma.window` 是 PostgreSQL 的**完全保留字**
   （`pg_get_keywords()` 的 `catcode = 'R'`），裸用直接语法错误，逼得两侧每条 SQL 都要引号包裹
   ——那正是「列名不可参数化」要消除的手工拼装。数据库列改名为 `bars`；**配置侧仍叫 `window`**
   （JSON 不受 SQL 关键字约束，R-12.1 的手感不变），两者只经 `quant_data.indicators._CONFIG_KEYS`
   一张表映射，多一个 / 少一个 / 大小写不同一律 `CONFIG_INVALID`。

2. **指标写入走 `COPY` + `INSERT … SELECT … ON CONFLICT`**（订正「向量化」的落地方式）。
   `executemany` 实测约 **170 行/秒**，15m 全量 216 万行要三个多小时；而同一批数据走
   staging 表 + `COPY` 只要 **91 秒**。1m 写入早就因为同样理由这么做（`pg.write_bars`），
   这里沿用同一条路径而不是引入第二种写法。读仍是廉价的、算仍是 O(段长)，只有写被优化。

3. **`upserted` 统计 `rowcount` 而不是 `len(rows)`**。UPSERT 带「值不同才更新」，
   `rowcount` 才是真正改动的行数；报 `len(rows)` 会让「发了多少条」冒充「落了多少行」，
   幂等断言（第二次必须为 0）就恒不成立。

### 6.3 实现过程中修掉的四个 bug（都是「不报错、只是数字不对」那一类）

| 症状                                                         | 根因                                                                                                                                   | 修法                             |
| ------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------- |
| 每个统计正好是真实值的 **2 倍**                              | `merge_stats` 里 `setdefault(key, item)` 在键缺失时把 `item` **本身**塞进结果，随后 `current.upserted += item.upserted` 成了自己加自己 | 无条件构造新对象再累加           |
| 指标物化 `INTERNAL_ERROR: tuple index out of range`          | `pk_values()` / `params_dict()` 拿主键列下标去索引 `params`，而 `kind` 占了一个主键列位置却**不占** `params` 下标                      | 用独立游标走 `params`            |
| `--check` 对 OBV 报 `syntax error at or near "ORDER"`        | 无参数指标的 `where` 是空串，硬拼 `AND {where}` 得到 `AND  ORDER BY`                                                                   | 空串时不加 `AND`                 |
| `COPY` 报 `expected 6 values in row, got 7`                  | `_copy_types` 对 `ma` 按「ma 就用 text」处理，漏了 `bars` 这一列                                                                       | 逐列判定 `text` / `int4`         |
| **`--check` 报出 156 万处 `mismatch`，偏差只有最后几位浮点** | 分批时按**固定步长**切窗口，把一个连续段从中间切成了两半（见下）                                                                       | 批边界对齐到段边界               |
| 物化进度停在 0 行不动                                        | 修上一条时「把未走完的尾段留到下一批」，返回的游标是**全局段首** → 同一段被反复重算                                                    | 改为**延长探测窗口**直到该段结束 |

前四条有个共同点值得记住：**它们都不会抛错、不会溢出，只是每个数字悄悄错一点或错一倍**。
而统计的唯一用途就是幂等断言——错一倍之后「第二次是 0」永远不成立，断言恒真。

### 6.3.1 第五条（最值得记的一条）：批边界必须落在段边界上

派生聚合的批对齐做法是「按**最宽的周期**推进，窄周期的桶被相邻两批各算一次，重复重算是幂等的」。
**指标不能照抄**。一个桶的值只取决于它自己那几根 1m，所以切批无害；但**一个连续段的值取决于整段**——
段被从中间切开之后，两半的「段首」不同，于是预热起点、递推种子、乃至浮点前缀和的原点全都变了：

```
同一根 15m bar，真实 close ≈ 6713.315999996662
按固定步长切批算出来的值：  6713.316000000001
```

偏差约 `3e-9`——**肉眼完全看不出来**，图也照样画得出来，但它足以让 `--check` 把每一行都报成
mismatch（15m 全库 156 万处）。而 `--check` 的全部价值就在于「一致时不报」，它一旦恒假就等于没有。

修法：每批先读一个探测窗口，若末段顶在窗口末尾就**按倍数外扩窗口直到该段结束**，
再整段写入；下一批从该段之后开始。段通常远小于窗口，实际只多读一次。
新增回归用例 `test_分批结果与整段重算逐值相同`（批大小 3 < 段长 9，刻意让固定步长必然切断段）。

### 6.3.2 性能：两处实测驱动的改动

| 改动                                                                                | 触发它的实测                                                                                                                             | 效果                                                                                              |
| ----------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------- |
| `executemany` → staging 表 + `COPY` + `INSERT … SELECT … ON CONFLICT`               | 15m 全量 216 万行在 `executemany` 下约 170 行/秒                                                                                         | **91 s**                                                                                          |
| 混版检查从「每批每周期每参数集」提到「每轮一次」                                    | 一轮首次全量可以有上千批，那条固定开销会被放大几千倍                                                                                     | 每批少 40 条往返                                                                                  |
| 连续段的「段起点 + 已读行」按连接缓存（`WeakKeyDictionary`）                        | 单批在生产规模上要重读 22 万根 15m（1.54 s）+ 找段首（1.02 s）                                                                           | 单批 **3.46 s → 1.1 s**                                                                           |
| 同一张指标表的多个参数集合并成一次 COPY + 一次 UPSERT（`RETURNING` 按参数分组统计） | `batch_size=500` 时每批 634 ms 几乎全是**语句往返**（4 周期 × 10 参数集 × 3 条），而真正写的行每批只有几十行                             | 4.3 万根 1m 的同步 **54.5 s → 30.0 s**                                                            |
| staging 表按连接只建一次                                                            | `CREATE TEMP TABLE IF NOT EXISTS` 每批被调用 7 指标 × 4 周期 = **28 次**，其中 27 次什么也没建——`IF NOT EXISTS` 让它安全，但**并不便宜** | 每批 **597 ms → 321 ms**（指标净增从 268 ms 降到 104 ms）；1.7 万根 1m 的同步 **52.0 s → 27.9 s** |

残余成本（**如实说明**）：增量路径按 R-4.2 必须「从段首重算」，而 RSI 的递推状态无法从
输出反推（A.3），因此单批代价与**所在段长度**成正比。BTCUSDT 的 15m 段有 22 万根，
稳定态下每批约 1.1 s；生产默认 `batchSize=5000` 时 4.3 万根 1m 的一轮约 6 s。
把这条彻底消掉需要让递推状态跨批携带（与 A.3 选定的无状态解冲突），本期不做。
