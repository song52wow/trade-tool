## A. 交易所事实

来源 `GET /fapi/v1/exchangeInfo` 与 `GET /fapi/v1/klines`。

### A.1 合约元数据（支撑 R-7 / R-8）

主文档 R-7 只需要三个字段：`contractType`、`status`、`onboardDate`。

| 标的       | `contractType` | `status`  | **`onboardDate`** |
| ---------- | -------------- | --------- | ----------------- |
| `SOLUSDC`  | `PERPETUAL`    | `TRADING` | 2024-01-03        |
| `BTCUSDC`  | `PERPETUAL`    | `TRADING` | 2024-01-03        |
| `DOGEUSDC` | `PERPETUAL`    | `TRADING` | **2024-01-18**    |
| `ADAUSDC`  | `PERPETUAL`    | `TRADING` | **2025-03-06**    |

→ **`onboardDate` 跨标的相差一年多**，且新标的持续上线。它**直接决定首次全量拉取的起点**（R-8），写死就会漏掉或越界。

全市场概况：

| 项                       | 值      |
| ------------------------ | ------- |
| `symbols` 总数           | 920     |
| `TRADING` 且 `PERPETUAL` | **571** |
| `timezone`               | `UTC`   |

→ 标的集合是**动态的**，任何白名单都会过期（R-5）。

`SOLUSDC` 的 `onboardDate` 原始值：`1704285900000` → 2024-01-03T12:45:00Z。

> `exchangeInfo` 同时返回 `tickSize` / `stepSize` / `minNotional` 等交易约束，
> 但**它们与「拉 K 线」无关**，主文档不作为任何逻辑的依据。

### A.2 端点与 K 线字段顺序（实现必需）

| 端点                        | 用途              | 结果                              |
| --------------------------- | ----------------- | --------------------------------- |
| `GET /fapi/v1/exchangeInfo` | 合约元数据（R-7） | 正常，**1.14 MB / 920 个 symbol** |
| `GET /fapi/v1/klines`       | 1m K 线（R-9）    | 正常，返回 12 字段数组            |

`exchangeInfo` 体积达 1.14 MB，因此 R-7 第 4 条要求**全进程共享单例缓存**，不得按标的重拉。

**K 线 12 字段顺序——接口不返回字段名，必须按位置解析：**

| 下标 | 含义               |
| ---- | ------------------ |
| 0    | open time (ms)     |
| 1    | open               |
| 2    | high               |
| 3    | low                |
| 4    | close              |
| 5    | volume（base）     |
| 6    | close time (ms)    |
| 7    | quote asset volume |
| 8    | number of trades   |
| 9    | taker buy base     |
| 10   | taker buy quote    |
| 11   | 忽略               |

**未知标的的错误响应**：`GET /fapi/v1/klines?symbol=SOLUSDCX` → `{"code":-1121,"msg":"Invalid symbol."}`

### A.3 限速与请求权重（支撑 R-20）

| 项               | 值                                    |
| ---------------- | ------------------------------------- |
| `REQUEST_WEIGHT` | **2400 / 分钟**（账号级）             |
| K 线单次上限     | **1500**（`limit=1501` 返回 `-1130`） |

**K 线请求权重分层（实测 `X-MBX-USED-WEIGHT-1M` 增量）：**

| `limit`     | 权重 | 实测增量 |
| ----------- | ---- | -------- |
| 1 – 100     | 1    | —        |
| 101 – 500   | 2    | +2       |
| 501 – 1000  | 5    | +5       |
| 1001 – 1500 | 10   | +10      |

### A.4 响应最后一根是「进行中」的 bar（支撑 R-10）

Binance 会把**当前进行中的 bar** 作为返回数组的**最后一个元素**。因此 R-10 要求无条件丢弃最后一根：

| 本地时钟 | 依赖 `closeTime <= now` 判定        | 丢弃最后一根 |
| -------- | ----------------------------------- | ------------ |
| 快       | ✘ 可能把进行中的 bar 当成已收盘存入 | ✔ 不受影响   |
| 慢       | ✔ 只是晚一轮拿到数据（无害）        | ✔ 不受影响   |
| 正常     | ✔                                   | ✔            |

→ 不需要额外的「交易所服务器时间」请求，也没有时钟同步问题。

## B. 1m 数据规模与缺口抽样

### B.1 规模与回补成本（支撑 R-8）

`SOLUSDC` 自 `onboardDate`（2024-01-03）至核验时约 **1004 天**：

| 项                            | 值            |
| ----------------------------- | ------------- |
| 1m bar 数                     | **1,445,410** |
| 单次请求上限（`limit`）       | **1500**      |
| 全量回补请求数                | **964**       |
| 全量回补权重（每次 10）       | **9,640**     |
| 按 1920 权重/分钟预算估算耗时 | **≈ 5 分钟**  |

→ 「首次全量」是 **964 次请求 / 约 5 分钟** 量级，不是「点一下就完」。
这就是 R-8 第 3 条要求**先计算并暴露规模**、R-8 第 4 条要求**默认 `paused`** 的原因
（否则一次添加 5 个标的 ≈ 4820 次请求）。

### B.2 连续性抽样（支撑 R-11）

对三个时间窗各取 1500 根 1m，检查相邻 `time` 差是否为 60,000 ms：

| 窗口              | bars | 缺口 |
| ----------------- | ---: | ---: |
| 近期              | 1500 |    0 |
| 2025-06           | 1500 |    0 |
| 2024-01（最早期） | 1500 |    0 |

→ 缺口应属**罕见**（计划维护、下线暂停）。「缺口即报错 + 自动回补」是安全网而非常态路径。

> **但必须注意**：R-9 的增量策略只看 `max(time)`，**本身不会发现历史中间的缺口**。
> 因此 R-11 要求**独立的缺口检测 + 自动回补**：
>
> - 检测必须是**增量**的（`[verified_upto, max(time)]`），不得每轮全表扫描；
> - 缺口**持久化**到 `gaps` 表，每轮优先回补，进程重启后仍能续做；
> - 回补**必须有尝试次数上限**（`maxGapAttempts`）——缺口虽罕见，但**永久性缺口**
>   （如交易所历史缺失）会对无限重试持续消耗配额并掩盖问题。达上限后进 `error`，由人工介入。
>
> 抽样缺口为 0 这个事实，正是「自动回补是安全网而非常态路径」的依据：
> 绝大多数轮次不会有缺口，检测成本只有一次增量扫描。

## C. PostgreSQL 存储

### C.1 为什么用 PG

| 需求                     | 文件方案                           | PG                                   |
| ------------------------ | ---------------------------------- | ------------------------------------ |
| **水位查询**（R-9 核心） | 读 sidecar 或扫全文件              | `SELECT max(time)`，**天然就是水位** |
| 并发写（R-3）            | 需**自己实现文件锁**               | `SELECT … FOR UPDATE` 行锁 + 事务    |
| 增量写入（R-9）          | 需整文件重写 + `rename` 才能推水位 | `INSERT … ON CONFLICT`，天然增量     |
| 缺口登记（R-11）         | 需自建 sidecar 并保证与数据一致    | `gaps` 表 + 事务                     |
| 大载荷传输（R-2）        | 需载荷分档（inline / file 双模式） | 数据不进桥接，stdout 只回小摘要      |
| schema 演进（R-1）       | 靠 sidecar 的 `schemaVersion` 自觉 | 迁移文件 + 版本表 + 启动校验         |

文件方案在**顺序读**上更快（`.npy` + mmap 读 1,445,410 行实测 **0.158 s**，体积 66.2 MB），
但上表每一行都要自己实现并保证一致性——这是改用 PG 的原因。

代价：**+ PG 服务 + `pg`（Node）+ `psycopg`（Python）**，并需要可重复的测试用 PG。

### C.2 体积估算（**估算值，未实测**）

PG 行存单行开销（窄表，`symbol` 已归一化）：

| 组成                                          | 字节            |
| --------------------------------------------- | --------------- |
| 元组头 + null 位图                            | ~24             |
| `time` int8 + 4×价格 float8 + `volume` float8 | 8 + 32 + 8 = 48 |
| 对齐填充                                      | ~8              |
| `(symbol, time)` 索引项                       | ~20             |
| **合计**                                      | **~100**        |

| 方案                                        | 单标的 1m 体积 | 38 标的     |
| ------------------------------------------- | -------------- | ----------- |
| `.npy`（实测基线）                          | 66.2 MB        | 2.5 GB      |
| **PG 行存（估算）**                         | **~144 MB**    | **~5.5 GB** |
| PG 行存 + `quote_volume` + `trades`（估算） | ~168 MB        | ~6.4 GB     |

→ **必须实测确认**。若不可接受，可选：减少列数
（`trades` / `quote_volume` 对「只拉 K 线」并非必需）、评估列存扩展，或对冷数据分层保留。
