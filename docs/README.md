# docs

本目录存放 `trade-tool` 仓库的设计与需求文档。

## 命名约定

需求文档一律以版本号开头，格式：

```
docs/v<MAJOR>.<MINOR>.<PATCH>-<kebab-case-主题>.md
```

例：`docs/v0.1.0-binance-perp-market-sync.md`

- 版本号与**本次需求所对应的交付版本**一致，不是文档自身的修订号。
- 同一版本内新增需求，用同一版本号加不同主题；对已有需求的修订，直接在原文件内更新，
  并在文末「修订记录」追加一行，不新建文件。
- 主题写**能力**而不是**样本**：写 `binance-perp-market-sync`，不要写 `binance-sol-usdc-perpetual`。
  具体标的属于验收样本，写在正文里，不进文件名。
- 文章正文的第一个章节必须是「文档信息」，其中**必须显式写明开发落在哪个 package**
  （本仓库是 monorepo，只写「哪个仓库」没有指导意义），并附上本次**不动**的 package 作为边界声明。

## 需求文档 / 调研附录 分离

需求文档**只写「要求什么」与「为何如此要求」**，目标 300 行以内。

实测数据、核验脚本、失败模式复现、性能对比等**证据**一律放进附录，命名加 `-appendix`：

```
docs/v0.1.0-<主题>.md            ← 需求：背景 / 范围 / 需求条目 / 验收标准
docs/v0.1.0-<主题>-appendix.md   ← 证据：实测数字 / curl 脚本 / 实验记录
```

理由：需求文档会被反复查阅，必须短；而证据需要完整保留以备复核。两者混在一起会同时
让需求文档过长、证据被淹没。需求文档中的**每一条结论性判断都应指向附录的具体小节**。
