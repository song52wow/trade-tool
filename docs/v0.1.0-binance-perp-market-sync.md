## 3. 需求条目

### 3.1 存储层（PostgreSQL）

#### R-1 schema 与迁移

1. 必须提供**版本化的迁移文件**，放在 `packages/data/sql/`，**纳入版本控制**。
2. 迁移必须**可重复执行且幂等**，且能从空库一路迁到最新版本。
3. 必须记录**已应用版本**（如 `schema_migrations` 表）；启动时检查版本，不匹配则报错，**不得静默按旧 schema 运行**。
4. 核心表：

   | 表                  | 主键 / 唯一约束       | 说明                                     |
   | ------------------- | --------------------- | ---------------------------------------- |
   | `klines_1m`         | `(symbol, time)`      | 1m K 线（表名即固化「只存 1m」的决定）   |
   | `contract_spec`     | `(exchange, symbol)`  | 合约规格快照（R-7 的解析结果）           |
   | `sync_state`        | `(exchange, symbol)`  | 同步状态、水位与 `verified_upto`（R-19） |
   | `gaps`              | `(symbol, gap_start)` | **待回补的缺口登记**（R-11 第 5 条）     |
   | `symbols`           | `(exchange, symbol)`  | 标的集合（R-18）                         |
   | `schema_migrations` | `version`             | 迁移记录                                 |

5. `klines_1m` 至少包含 `symbol` / `time` / `open` / `high` / `low` / `close` / `volume`，
   以及可选的 `quote_volume` / `trades`。
6. **时间戳类型必须统一为 `bigint`（epoch 毫秒）**，不用 `timestamptz`——
   仓库跨语言契约与全部既有代码都用毫秒时间戳，混用会引入时区 bug。
7. 必须有 `(symbol, time)` 上的**唯一约束**——增量路径的 UPSERT 与缺口回补的 `DO NOTHING` 都依赖它（R-9 / R-11）。
8. 1m 数据量最大（约 144 万行/标的），必须评估并按需建立 **BRIN 索引或按 symbol / 时间分区**（体积估算见附录 C.2）。

#### R-2 跨语言接缝 = 数据库

1. **K 线数据只经 PG 传输**，不经 stdout / JSON 承载。
   `packages/data` → `python -m quant_data` 的桥接**只传控制信息**：触发命令、参数、执行结果摘要（行数、时间范围、状态码）。
2. 因此 `bridge.ts` 的 `maxBuffer` **不再是数据量的约束**。
   但仍必须保留：**桥接不得承载大载荷**，超出小摘要规模的结果一律落库后返回引用。
3. **数据库 schema 就是新的跨语言契约**：改 schema 必须同提交更新两侧的读写代码与迁移文件（AC-25）；
   两侧必须对同一列的**类型、单位、NULL 语义**达成一致（见 R-4）。
   仓库 `README.md` 的「跨语言契约」需相应重写。
4. **依赖方向不变**：`apps/sync` **不得**绕过 `packages/data` 直接连 PG 执行写入，
   写入只能经 `packages/data`（AGENTS.md：跨语言调用只从 `packages/data` 发起）。
5. **不得**让两端各自持有 schema 的「影子定义」——表结构以迁移文件为唯一来源。

#### R-3 批量写入、事务与并发

1. 首次全量回补（约 144 万行/标的）**必须使用 `COPY`**，不得逐行 `INSERT`。
2. 写入必须**分批提交**（批大小可配置），每批一个事务；
   **成功提交后才推进水位**（R-19），保证中断后不重头、不丢数。
3. **同一标的的写入必须串行**。依赖 PG 的唯一约束保证幂等，
   但**不得**依赖「两个进程同时写同一标的安全」——必须在应用层保证单写者（如对 `sync_state` 行 `SELECT … FOR UPDATE`）。
4. 多标的写入可并发，但必须共用全局配额限速器（R-20）。
5. 写入失败必须**整批回滚**，不得留下半批数据。
6. 必须能查询写入进度（已入库行数 / 目标行数）。

#### R-4 NULL 语义

> 库中只有 K 线，所以 NULL 只剩一种可能：**交易所确实没提供该字段**。

1. **`time` / `open` / `high` / `low` / `close` / `volume` 必须为 `NOT NULL`。**
   这些列出现 NULL 即为数据损坏 → 写入与读取都必须**报错**，不得静默。
2. `quote_volume` / `trades` **允许 NULL**，语义严格定义为「**交易所未提供该字段**」。
3. **禁止**用 `0` 代替缺失（`0` 是合法成交量）。
4. 读取侧必须能区分「该字段为 NULL（交易所未提供）」与「该行不存在（区间未同步）」。

### 3.2 K 线拉取与续传

#### R-5 标的不写死（硬约束）

1. 代码中**不得出现**任何具体合约名的字符串常量（测试 fixture 除外）。
2. 不得有标的白名单、`if symbol == ...` 分支、按标的区分的特例逻辑。
3. 不得内置任何标的的元数据数值（`onboardDate` / 合约状态等）。
4. 标的**不得**加枚举白名单——标的集合是动态的（实测 571 个 TRADING 永续且在变化）。

#### R-6 周期固定 1m

1. **周期固定 `1m`，不提供 `interval` 配置项**（本期只拉 1m，见 N-1）。
2. 不要保留一个永远只有单个取值的枚举或参数——**该约束体现在 schema 表名上**（R-1 第 4 条）。

#### R-7 交易所元数据运行时解析

1. `exchangeInfo`（实测 1.14 MB / 920 个 symbol）**必须缓存**（磁盘或 PG 表），TTL 默认 1 小时；
   命中时记录 age；TTL 过期且拉取失败时允许用过期缓存，但必须 `WARN` 且标记 `metadataStale`。
2. `symbol` **精确匹配**（大小写敏感，不做模糊匹配或自动补全猜测）。校验失败给出结构化错误码：
   `SYMBOL_NOT_FOUND` / `NOT_PERPETUAL` / `NOT_TRADING` / `METADATA_FETCH_FAILED`。
3. **本需求只依赖三个字段**：`contractType`、`status`（用于 R-7 第 2 条的校验）与 `onboardDate`（用于 R-8 的首次全量起点）。
   三者**一律不得硬编码**。其余规格字段（`tickSize` 等）与本需求功能无关，可随解析结果一并存入 `contract_spec` 作为快照，但不作为任何逻辑的依据。
4. **元数据是全进程共享的单例**，不得按标的各拉一份——多标的并发时按标的重拉会立刻打满配额。

#### R-8 首次拉取：必须全量

1. **「已存在历史」的判定 = `klines_1m` 中该 symbol 有行**（`SELECT max(time)` 非空）。
2. **无历史时（首次拉取）必须全量**：从该标的的 `onboardDate`（**运行时读取**，R-7 第 3 条）起算，一直拉到最新。
   **不提供缩短首次范围的配置项**——首次就是要完整历史。
3. 首次拉取前**必须先计算并暴露规模**：约 N 根 / 约 M 次请求 / 约 S 分钟（按限速估算）。
   依据：SOLUSDC 全量约 **964 次请求 / 约 5 分钟**（附录 B.1）。
   - CLI：执行前打印并需显式确认；
   - 常驻：写入 `sync_state`，由 `sync status` 暴露，控制面据此决策。
4. 常驻模式下**新增标的默认 `paused`**，需控制面显式开启才启动首次全量——
   避免一次添加多个标的引发回补风暴。一次添加 5 个标的 ≈ 4820 次请求。
5. 首次全量必须支持**断点续传**：分批提交，中断后从水位继续，不重头（R-3 第 2 条）。
6. 首次全量的进度必须可查询（已入库行数 / 目标行数）。

#### R-9 增量续传（本需求的核心）

1. **水位定义**：`watermark = SELECT max(time) FROM klines_1m WHERE symbol = ?`。
   > **注意：不加 `60_000`。** 起点**包含**最后一根已存 bar，使其被重新拉取——
   > 这是「最后一根必须重拉并覆盖」的实现方式（R-9 第 4 条）。
2. 请求时用 `startTime = watermark`；`endTime` 不指定（拉到最新）。
3. **写入策略由「起点」决定**——这是保证「更早的历史不可被改写」的关键规则：

   | 起点                   | 场景            | 冲突处理                     |
   | ---------------------- | --------------- | ---------------------------- |
   | 起点 **= `max(time)`** | 增量续传（R-9） | `ON CONFLICT DO UPDATE`      |
   | 起点 **< `max(time)`** | 指定区间 / 回补 | **`ON CONFLICT DO NOTHING`** |

   增量的起点就是 `max(time)`，返回的 bar 全部 `>= max(time)`，
   所以 UPSERT **唯一会覆盖的已有行就是「最后一根」**——效果正好是「只追加 + 最后一根覆盖」。
   **起点一旦早于 `max(time)`，就必须退化为 `DO NOTHING`**，否则会静默改写历史（R-12 / R-15）。

4. **必须校验返回数据的边界**：所有 bar 必须满足 `time >= startTime`。
   违反即抛错（错误码 `BACKFILL_BOUNDARY_VIOLATION`）——
   防止交易所忽略 `startTime` 时 UPSERT 静默改写了历史数据。
5. **无新数据时不报错**：丢弃最后一根（R-10）后若仅剩那根已存的 bar，UPSERT 它是幂等的，
   正常返回 `added = 0`。
6. 水位**必须由库内数据推导**，不得单独维护一个可能与数据不一致的计数器。
   `sync_state.watermark`（R-19）只作为**可观测缓存**，权威来源始终是 `max(time)`。
7. 水位单调不减：任何一次成功写入后 `max(time)` 必须 ≥ 写入前的值。

#### R-10 只存已收盘 bar

1. **必须丢弃响应中的最后一根**——Binance 会把**进行中的 bar** 作为最后一个元素返回（附录 A.4）。
   这比依赖本地时钟更稳：本地时钟快或慢都不会导致存入未收盘 bar。
2. 丢弃后若为空，按 R-9 第 5 条处理（已是最新，`added = 0`）。
3. **库内最后一根的 `closeTime > now` 由重拉自愈**：
   这属于历史脏数据（旧版本写入、时钟异常）。因 R-9 的起点包含最后一根，重拉 + UPSERT 会覆盖修正它。
   修正后必须**再校验一次**；若仍不满足则抛错（`UNCLOSED_BAR_IN_STORE`），**不得静默继续**。
4. 校验应允许注入 `now_ms`，便于单测固定时钟。

#### R-11 缺口：只追加 + **自动补缺口**

> **这是「按历史最新时间开始拉取」的必要补偿。**
> 增量策略只看 `max(time)`，本身不会发现历史中间的缺口；
> 因此必须独立地**检测并自动回补**，同时保证检测成本不随数据量线性增长。

**A. 增量检测（成本受控的关键）**

1. **必须能检测缺口**：校验相邻 `time` 差是否为 `60_000`。检测用 SQL 完成（窗口函数 `lag()`），
   **不得**把全部行拉到应用层（144 万行）。
2. **检测范围必须是增量的**：`sync_state` 维护 `verified_upto`（已知连续到的时间点，含）；
   每轮只扫描 `[verified_upto, max(time)]`，**不得每轮全表扫描**。
3. **全表扫描只在两种情况下执行**：① 首次为某标的建立 `verified_upto` 基线；
   ② 显式命令 `data verify --symbol`（用于发现「已验证区间之后被外部改动」的情况）。
4. 扫描未发现缺口时，推进 `verified_upto = max(time)`。

**B. 缺口的持久化与自动回补**

5. **发现的缺口必须持久化**到 `gaps` 表（R-1 第 4 条）：
   `symbol` / `gap_start` / `gap_end` / `missing_rows` / `attempts` / `last_attempt_at` / `last_error`。
   > 持久化是必需的：缺口可能跨越多次同步轮次，且进程会重启。
6. **每轮同步必须优先回补已登记的缺口**，再拉增量——否则缺口永远排在增量之后，可能长期滞留。
7. 缺口回补用分页拉取 + 批量写入；**写入使用 `ON CONFLICT DO NOTHING`**
   （缺口区域本无行；`DO NOTHING` 更安全，绝不误改已存在的正确数据）。
8. 回补成功后删除该 `gaps` 记录；若该缺口与 `verified_upto` 相邻，则推进 `verified_upto`。
9. **回补尝试次数必须有上限**（`maxGapAttempts`，默认 5）。
   达到上限后该标的进入 `error` 状态，**停止自动回补**，需控制面显式恢复。
   > 没有上限的自动回补会对**永久性缺口**（如交易所历史缺失）无限重试，持续消耗配额并掩盖问题。

**C. 共同约束**

10. **禁止插值补齐**、禁止跳过、禁止只打 `WARN`。缺口**只能由真实数据填充**。
11. 缺口不得静默存在：必须能查询**缺口清单与缺失总行数**（`sync status` / `data gaps`）。
12. **必须保留人工兜底入口** `data backfill --symbol --from --to`，
    用于自动回补达上限后的人工干预（R-15）。

#### R-12 幂等与去重

1. 同一区间重复执行拉取 → `added = 0`，**不产生重复行**。
2. **增量路径（起点 = `max(time)`）用 UPSERT**：重复写同一根 bar 结果相同（值来自交易所，确定性）。
3. **起点早于 `max(time)` 的一切写入（指定区间 / 缺口回补）一律用 DO NOTHING**：绝不改已存在的行。
4. 分页响应中相邻页可能重叠 → 按 `time` 去重后再写入。
5. 同一标的并发执行两次拉取 → 被 R-3 第 3 条串行化或拒绝，**不得产生重复数据**。
6. 幂等性必须有测试覆盖（AC-5）。

#### R-13 配置

| 段         | 字段                                                                                                           |
| ---------- | -------------------------------------------------------------------------------------------------------------- |
| `market`   | `exchange`、`marketType`、`symbol`、`source`                                                                   |
| `data`     | `python`、`metaDir`、`metadataTtlMs`、`allowStaleMetadata`、`timeoutMs`、**`batchSize`**、**`maxGapAttempts`** |
| `database` | 连接参数（host / port / db / user / password / poolMax）；密码**必须经环境变量注入，不得写入配置文件**         |
| `sync`     | 标的集合、每标的期望状态、并发上限、退避参数（R-17 … R-22）                                                    |

1. `defaultConfig()` 保持 `synthetic`，现有离线链路与测试不得回归。
2. **无 `interval` 字段**（R-6）。
3. **无「首次范围」字段**——首次必须全量（R-8 第 2 条）。

### 3.3 工程

#### R-14 失败语义

**A. 一次性命令（`apps/cli`）**

1. `source: 'binance'` 时**任何**失败都必须抛错并以非 0 退出码结束；**绝不回退到 `generate_series`**。
2. `source` 必须显式给出，**不设隐式默认**。
3. 失败时 **stdout 不输出任何内容**，stderr 给出可读原因（含结构化错误码与交易所 `code` / `msg`）。

**B. 常驻进程（`apps/sync`）**

4. **单标的失败必须被隔离**：网络、解析、PG 写入、缺口错误**不得**终止进程，也不得影响其他标的。
   状态置 `error` 并记录 `lastError`，按 R-21 退避后重试。
5. 进程仅在**全局性**错误时退出（配置非法、**PG 不可连**、元数据无法获取且无可用缓存、schema 版本不匹配）。
6. 「不静默兜底」在常驻形态下体现为**状态可查 + 错误上报**（R-19），而不是进程退出。

#### R-15 CLI

```
trade-tool db migrate                                              # 应用迁移
trade-tool data fetch --source <synthetic|binance> --symbol <SYMBOL> [--bars <N>]
trade-tool data sync --symbol <SYMBOL> [--from <ms>] [--to <ms>]   # 增量续传（本期主入口）
trade-tool data backfill --symbol <SYMBOL> --from <ms> --to <ms>   # 显式回补缺口
trade-tool data verify --symbol <SYMBOL>                           # 全表缺口扫描（重建 verified_upto 基线）
trade-tool data gaps --symbol <SYMBOL> [--json]                    # 查看待回补缺口清单
trade-tool data symbols [--source binance] [--json]
trade-tool sync status [--symbol <SYMBOL>] [--json]
```

1. `--symbol` **不做枚举校验**，合法性由运行时元数据判定。
2. `data sync` 不传 `--from` 时是**增量**语义（起点 = `max(time)`，UPSERT）；
   传 `--from < max(time)` 时退化为**区间补数**语义（DO NOTHING，绝不覆盖已有行）。见 R-9 第 3 条。
3. `db migrate` 必须幂等；schema 版本不匹配时其他命令**必须报错**而不是继续运行。
4. `apps/cli` 保持**一次性命令**语义（R-14 A）。**生命周期控制不走 CLI 写入命令**，走 R-22 的原语。

#### R-16 测试

1. `packages/data` 补 `"test": "vitest run"` + `vitest` 依赖 + `tests/` 目录。
2. **必须提供可重复的测试用 PG**（容器或本地实例），测试**不得连生产库**；
   测试必须能**从空库执行迁移**并在结束时清理。
3. Python 侧必须有 `metadata` / `binance` / **增量续传** / **PG 写入**的单测。
4. `apps/sync` 必须有生命周期、全局限速、单写者、错误隔离、状态往返的单测。
5. 所有网络调用**必须可注入 mock transport**，测试过程中**不得访问真实网络**。
6. 用例**必须参数化到多个标的**；常驻相关用例**必须参数化到多标的并发**。
7. **必须包含**：迁移幂等性、`COPY` 批量写入与断点续传、**增量水位正确性**（重复执行 `added=0`）、
   **丢弃最后一根**（注入固定时钟）、**缺口增量检测与自动回补**、**写入策略随起点切换**、幂等与去重。

### 3.4 常驻同步（前端控制）

#### R-17 同步生命周期（幂等）

1. 每个标的的状态机：`paused` ↔ `running` → `error`（R-21）。
2. **开启 / 暂停 / 恢复**三个原语，**全部幂等**——控制面可能重复发送。对已是目标状态的请求返回当前状态而非报错。
3. 状态变更必须**先持久化再生效**（R-19）。
4. 新建标的默认 `paused`（R-8 第 4 条）；首次开启时才启动首次全量。
5. 暂停**不删除**任何数据。
6. 生命周期操作必须**立即返回**，不得阻塞等待回补完成。

#### R-18 标的集合管理

1. 标的集合可增删，**运行时生效**，无需重启进程；落在 `symbols` 表（R-1）。
2. 新增标的必须先经 R-7 元数据校验，失败**不得**写入集合。
3. 移除标的时数据处置必须**显式定义且可配置**（保留 / 归档 / 删除）；**禁止**静默删除已入库数据。
4. 标的集合本身必须持久化，且与每标的状态一同可查询。
5. 重复添加同一标的必须幂等。

#### R-19 状态持久化与可查询

1. 每标的至少持久化并可查询（`sync_state` 表）：
   `symbol` / `status` / `watermark` / **`verified_upto`** / `rows` / `bytes` /
   `lastRunAt` / `lastSuccessAt` / `lastError` / `errorCount` / `backoffUntil` / **`pendingGaps`**。
2. `verified_upto`（已知连续到的时间点）是**缺口增量检测的基线**（R-11 第 2 条），
   必须与数据一起持久化；进程重启后必须仍然准确，否则会漏检或重复全表扫描。
3. `pendingGaps`（待回补缺口数）必须可查询，使缺口状态对控制面可见（R-11 第 11 条）。
4. 状态必须在**进程重启后仍然准确**。重启后：`running` 的继续增量同步；`paused` 的保持暂停；
   已登记的 `gaps` 继续参与自动回补。
5. 状态更新与**该批数据写入必须在同一个事务内**——否则会出现「数据已入库但水位未推进」或反之。
6. `sync_state.watermark` 是**可观测缓存**，权威水位始终由 `max(time)` 推导（R-9 第 6 条）；
   二者不一致时必须**报错**而不是二选一。
7. schema 版本不匹配时**不得**按旧结构继续运行（R-1 第 3 条）。
8. 必须能查询**全局汇总**：标的数、各状态计数、入库总体积、待回补缺口总数、当前配额使用率。

#### R-20 全局配额与并发控制

1. **权重预算必须是进程级全局的**，不是每标的一份。附录 A.3 的 2400/分钟是**账号级**配额。
2. 所有出网请求都必须经过**同一个限速器**。
3. 预算上限建议为配额的一定比例（如 80%），留余量给人工排查。
4. 必须能查询**当前窗口的配额使用率**。
5. 并发度可配置且有上限；同一标的同时只允许一个同步任务（R-3 第 3 条）。
6. 批量回补**不得**一次性放开全部并发，必须排队通过限速器。
7. **PG 连接池必须有上限**，且与并发标的数、批大小一并配置——多标的并发时连接耗尽是常见故障。

#### R-21 错误隔离与退避

1. 单标的失败**不扩散**：不影响其他标的，不终止进程（R-14 B）。
2. 失败后按**指数退避**重试，退避上限可配置；退避期间该标的不参与调度。
3. 连续失败达阈值后进入 `error` 状态并**停止自动重试**，需控制面显式恢复。
4. 交易所返回 **429 / 418** 时尊重 `Retry-After`，并**全局暂停**所有出网请求（配额是账号级的）。
5. 缺口错误（R-11）与未收盘 bar 错误（R-10 第 3 条）属于**需人工介入**的错误：
   不得自动重试掩盖，必须保持 `error` 并在 `lastError` 中给出位置信息。
6. **PG 错误须单独分类**：连接失败 / 唯一冲突 / 事务回滚 / 死锁。
   - 连接失败 → 退避重试，**不消耗**交易所配额；
   - **死锁 → 有限重试**（PG 会回滚其中一个事务，属可恢复）；
   - schema 不匹配 → **立即停止**，不得重试。

#### R-22 控制原语接口（交付边界）

1. `apps/sync` 必须导出程序化原语，至少覆盖：
   - 标的集合：`addSymbol` / `removeSymbol` / `listSymbols`
   - 生命周期：`start` / `pause` / `resume`（全部幂等，R-17）
   - 状态查询：`getStatus(symbol?)` / `getSummary()`
2. 原语必须**类型完整**（供控制面直接 import），且**不依赖任何 HTTP 框架**。
3. 原语必须同时**进程内可调用**与**可通过 `apps/cli sync status` 观测**。
4. 原语的错误必须结构化，不得只返回字符串。
5. 控制面**不需要**了解 PG schema、回补队列、退避策略的任何内部细节——这是控制面的边界判据。
6. 状态必须已经落库（R-19），使跨进程协作不需要引入新的通信机制。
