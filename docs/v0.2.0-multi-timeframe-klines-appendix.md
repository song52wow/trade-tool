## A. 桶对齐

### A.1 为什么 `t - (t mod W)` 就够

四个桶宽都整除一天：

| 周期 | W (ms)     | 86400000 / W |
| ---- | ---------- | ------------ |
| 15m  | 900 000    | 96           |
| 1h   | 3 600 000  | 24           |
| 4h   | 14 400 000 | 6            |
| 1d   | 86 400 000 | 1            |

epoch 0（`1970-01-01T00:00:00Z`）本身是 UTC 零点，因此 `floor(t / W) * W` 得到的边界
与 UTC 日历边界逐点重合，不需要任何时区参与。主文档 R-2.1 要求用取模而不是
`date_trunc`，原因就在这里：`date_trunc('day', …)` 的结果取决于会话 `TimeZone`，
换个连接参数同一条 SQL 就会给出另一组边界，而取模永远只有一种结果。

### A.2 边界值（可用于参数化单测）

| 周期 | 输入 `t` (ms) | `bucket_start` (ms) | UTC 含义                         |
| ---- | ------------- | ------------------- | -------------------------------- |
| 15m  | 1735689600000 | 1735689600000       | 2025-01-01T00:00:00.000          |
| 15m  | 1735689899999 | 1735689600000       | 00:04:59.999 → 桶 00:00          |
| 1h   | 1735693199999 | 1735689600000       | 00:59:59.999 → 桶 00:00          |
| 4h   | 1735703999999 | 1735689600000       | 03:59:59.999 → 桶 00:00          |
| 4h   | 1735704000000 | 1735704000000       | 04:00:00.000 → 桶 04:00          |
| 1d   | 1735775999999 | 1735689600000       | 当日 23:59:59.999 → 桶当日 00:00 |

第 4、5 行是一对刻意选的边界：**跨过 04:00 的前一毫秒仍属 00:00 桶，整点那一毫秒才换桶**
（`1735703999999 mod 14400000 = 14399999`、`1735704000000 mod 14400000 = 0`）；
最后一行是 1d 的当日边界。用「按小时切片再拼」或「本地时区截断」的实现会在这两处露馅。

## B. 规模

### B.1 行数（算术推导，未实测）

以每标的每年（365 天）计：

| 表           | 桶/天 | 桶/年   |
| ------------ | ----- | ------- |
| `klines_1m`  | 1440  | 525 600 |
| `klines_15m` | 96    | 35 040  |
| `klines_1h`  | 24    | 8 760   |
| `klines_4h`  | 6     | 2 190   |
| `klines_1d`  | 1     | 365     |
| 派生合计     | —     | 46 355  |

派生表总行数约为 1m 的 **8.8%**（46 355 / 525 600）。这是 N-8「先不分区分表」的依据，
但**必须以实测行数复核**（同步过的标的往往不足整年，尤其是新上市品种）。

### B.2 体积（估算，未实测）

沿用 v0.1.0 附录 C.2 的 ~100 字节/行（含索引摊销）只是**同一口径的推算**，
不是实测：派生四表约为 `46 355 × 100 B ≈ 4.6 MB`/标的/年，相对 1m 的 ~52.6 MB 仍是 8.8%。

先前的教训必须结清：`sync_state.bytes` 一直按估算推进，谁都没有量过真表。
本次要求汇总里的派生体积直接读 `pg_total_relation_size`（主文档 R-8.2 / AC-16），
并把测得的数字回填到这张表。

## C. 覆盖判据的边界情形

主文档 R-3 的判据（`closed && actual == expected`，`win` 取桶与该标的 1m 区间的交集）
在四种边缘下的行为：

### C.1 onboard 首日

SOLUSDC 的 `onboardDate = 1704285900000` → 2024-01-03T12:45:00Z（v0.1.0 附录 A.1）。
当天的 1d 桶 `b = 1704240000000`（2024-01-03T00:00:00Z），`F` 落在 12:45，
因此 `win = [12:45, 23:59]`、`expected = 675`（不是 1440）。
该桶**应当**被写入——如果实现里写死「一天必须 1440 根」，这个标的的第一根日线将永远不存在。
这是一条只能用真实样本发现的边界，故 `SOLUSDC` 被列为主验收样本。

### C.2 数据末端

`L` = 最后一根已入库的 1m（它本身一定是已收盘 bar，v0.1.0 R-10.1）。

| `L` 的位置                       | `closed` | 结果               |
| -------------------------------- | -------- | ------------------ |
| 桶中途（最常见）                 | false    | 不写，等下一批 1m  |
| 恰好是桶的最后一分钟             | true     | 当轮写入           |
| 桶最后一分钟已收盘但 1m 还没入库 | false    | 不写（不猜、不造） |

第二、三行的区别就是「不读本地时钟」的代价与收益：判据只看库内数据，
所以「交易所已收盘、我们还没拉到」这一小段时间里，桶**晚一点**出现，而不会早出现或凭空出现。

### C.3 桶内有缺口

`actual < expected` → 不写。这会把 1m 的缺口原样投影成高周期的空白，
正是主文档 R-3.5 要的效果：图上少一根 4h 蜡烛，比画一根少了 30 分钟数据的 4h 蜡烛更容易被发现。
被扣留桶数与 `missingMinutes` 必须报出来（R-5.6），否则「少一根」仍然需要人去猜。

### C.4 桶完全在数据区间之外

`win` 为空（桶整个早于 `F` 或晚于 `L`）→ 不参与统计，也不写。
这条保证 `expected` 不会出现 0 或负数，避免除零与「空桶算合格」的边界错误。

## D. 核验 SQL

以下查询是 AC-1 / AC-2 / AC-5 / AC-16 的落地形态，可直接在测试库里跑。
`$1` 为标的，`14400000` 为 4h 的 W，换周期时替换该常量。

### D.1 列结构逐列相等（AC-1）

对称差为空才算通过：

```sql
SELECT column_name, data_type, is_nullable FROM information_schema.columns
 WHERE table_name = 'klines_1m'
EXCEPT
SELECT column_name, data_type, is_nullable FROM information_schema.columns
 WHERE table_name = 'klines_15m';
```

反向再做一次（`klines_15m EXCEPT klines_1m`），四张派生表各一轮。

### D.2 桶值逐值比对（AC-2）

重算 4h 桶并与 `klines_4h` 对拍，返回行即不一致：

```sql
WITH recomputed AS (
  SELECT symbol,
         time - (time % 14400000) AS bucket,
         (array_agg(open  ORDER BY time ASC ))[1] AS open,
         max(high)                                AS high,
         min(low)                                 AS low,
         (array_agg(close ORDER BY time DESC))[1] AS close,
         sum(volume)                              AS volume
    FROM klines_1m
   WHERE symbol = $1
   GROUP BY 1, 2
)
SELECT k.time
  FROM klines_4h k
  JOIN recomputed r ON r.symbol = k.symbol AND r.bucket = k.time
 WHERE (k.open, k.high, k.low, k.close, k.volume)
       IS DISTINCT FROM (r.open, r.high, r.low, r.close, r.volume);
```

注意：`recomputed` 里也包含未收盘与未全覆盖的桶，**它只能用来对拍已写入的行**，
不能反过来当合格性判据；合格性一律以主文档 R-3 为准。

### D.3 派生表里的「多出来的桶」（AC-9 的 --check 用）

```sql
SELECT k.time FROM klines_4h k
 WHERE k.symbol = $1
   AND k.time + 14400000 > (SELECT max(time) FROM klines_1m WHERE symbol = $1) + 60000;
```

返回的行就是「1m 还没走完却已经写进派生表的桶」——按 R-3.3 不应存在。
反向的「该有却没有」需要按桶步进生成序列再左连接，属于 `--check` 的实现细节，此处不展开。

### D.4 实测体积（AC-16）

```sql
SELECT relname, pg_total_relation_size(oid) AS bytes
  FROM pg_class
 WHERE relname IN ('klines_1m', 'klines_15m', 'klines_1h', 'klines_4h', 'klines_1d')
 ORDER BY relname;
```

结果回填 B.2，并把该表从「估算」改为「实测」。

### E.1 已回填：单批聚合耗时

30 天 / 43 200 根 1m，四个周期（`15m` + `1h` + `4h` + `1d`），每批 500 根，
**含事务提交**（脚本：`quant_data.aggregate.aggregate_batches` 走真实连接）：

| 场景                                    | 耗时            |
| --------------------------------------- | --------------- |
| 首次全量（桶尚不存在，`before` 为空）   | **211 ms / 批** |
| 增量（桶已存在，需整桶齐全 + 写前集合） | **327 ms / 批** |

两项优化各自的效果：

1. **四个周期共用一次 1m 读取**——四个周期读的是同一批行，逐周期各读一遍等于把最贵的
   查询做四遍。改由 `aggregate_batches` 按最宽周期读一次，各周期在内存里各自切桶。
2. **`upserted` 不再查「写后桶集合」**——`ON CONFLICT DO UPDATE` 的 rowcount 恒等于
   受影响行数，用它当幂等断言会假失败；改成「实际落库的桶 − 写前已有的桶」后，
   答案已由写入列表与写前集合给出，省掉一次范围查询。

**行数校正**：`upserted` 不能用 `conn.rowcount`。重复执行同一区间时每行都是一次真实的
UPDATE，rowcount 仍等于行数——那会让「第二次 `upserted = 0`」这条幂等断言恒假。

**为什么增量比首次全量更贵**：扣留统计与整桶齐全判定需要全区间 `GROUP BY`，而增量场景
桶已存在，`whole_buckets` 那次查询不能省（首次全量 `before` 为空，直接跳过）。

> 早期曾用一个**纯内存微基准**测出过一个显著更低的单批耗时。那个基准跳过了事务提交与
> 1m 实际读取路径，不代表真实链路；以上表的端到端数字为准。此条保留是为了让后来者
> 知道早期那个数字错在哪。

### E.2 已回填：端到端耗时（AC-2 集成用例）

`sync-integration.test.ts` 的 AC-2（30 天首次全量，走真实 Python 引擎 + 真实 PG）：

| 版本             | 耗时   |
| ---------------- | ------ |
| 改动前（v0.1.0） | 约 9 s |
| 加派生层后       | 17.5 s |

聚合挂在每批写入上（R-4.1），所以它的常数因子直接乘在同步耗时上。**这是本期唯一的显著
性能代价**：多约 8 秒换四个派生周期。`AC-10 多标的全量`（三个标的、22.6 万根、120 s 预算）
在这条曲线下仍有余量。

### E.3 仍未实测

- **D.4 的四张派生表实测体积**：AC-16 的测试已断言 `derived.bytes` 等于
  `pg_total_relation_size(to_regclass(...))` 的返回值（因此「读的是实测值而非估算」
  这件事本身已被测试覆盖），但**具体字节数**取决于测试库里的实际数据量，
  拿测试库的数字当容量规划依据是不对的。生产库跑一次 `sync status` 即可回填 B.2。
- **全量重建耗时**：`aggregateBatchBars` 默认 20 000 的依据是「单事务的锁持有时间与
  WAL 体积可接受」，尚未在真实数据量上量过 `--rebuild` 的墙钟时间。
- **BRIN 在 `klines_1d` 上的收益**：`klines_1d` 每标的每年仅 365 行，BRIN 索引可能
  比主键扫描还慢（附录 E 第 5 行）。本期按 R-1.3「与 1m 同形」实现，收益未测。
