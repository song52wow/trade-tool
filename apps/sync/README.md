# @trade-tool/sync

常驻行情同步守护进程（R-17 … R-22）。

- `src/primitives.ts` — 控制原语：`addSymbol` / `removeSymbol` / `listSymbols` /
  `start` / `pause` / `resume` / `getStatus` / `getSummary`。**全部幂等、全部类型完整、
  不依赖任何 HTTP 框架**，供控制面直接 import。
  新增标的默认 `paused`，并且在**开启之前**就把首次全量的规模预估写进 `sync_state`
  （`plan_*` 列，迁移 `002`），由 `sync status` 暴露——控制面据此决定要不要开始。
- `src/daemon.ts` — 调度循环：标的集合、生命周期、全局限速、单写者、错误隔离、退避。
  启动时先过 schema 版本闸门；每轮按 `last_run_at` **公平轮转**，并发上限之外的标的不回饿死；
  单标的失败只在它自己的状态里落地，绝不终止进程。
  **慢标的不堵住别人**：一轮是「**启动**该跑的标的」而不是「等它们跑完」——
  见下面那一节。
- `src/service.ts` — `createSyncService()`：把「原语 + 守护进程 + 连接池」组装起来。
  **控制面与守护进程共享同一个 `SyncControl` 实例**，否则 `resume()` 清不掉守护进程的退避。
- `src/main.ts` — 进程入口（`bin: trade-tool-sync`）。配置里的 `sync.symbols` 支持两种写法：
  `"SOLUSDC"`（默认 paused）或 `{ "symbol": "SOLUSDC", "desiredState": "running" }`。

所有写入都经 `@trade-tool/data`，本包**不得**直接连 PG（R-2.4）。

## 慢标的不堵住别人（2026-10-23 修）

### 原来坏在哪

一轮同步 = 把「上次水位 → 现在」的数据**一次拉完**（`batch-size` 只是**写库**的批次大小，
不是拉取上限）。所以一个标的的**首次全量回补**动辄几百页 HTTP 请求，实测一轮 11~15 分钟。

而调度循环原来写成「等这一轮**全部**标的跑完才进下一轮」（`await Promise.all(workers)`），
于是这个慢任务把整个循环钉住：**别的标的十几分钟才被调度一次**。

2026-10-23 在目标机上实测到的样子：BTCUSDT / SOLUSDT 的 1m K 线落后 10~15 分钟
（用户看到的是「同步停在 7 分钟前」），而根因只是**另一个**标的（BNBUSDT）在做它的
首次全量回补。数据没坏、程序没卡死——只是队列被一个慢任务堵住了。

### 现在怎么做的

一轮 = **启动**该跑的标的，然后立刻返回。每个标的各跑各的，跑完自己摘掉并发名额；
循环每 `sync.pollIntervalMs` 扫一次，把空闲名额分给还没跑的标的。

慢标的照旧占着自己的名额（**并发上限依然成立**），但不再挡住别人。

三条要记住的：

- **名额即释放**：任务跑完就从在途表里摘掉，空出来的名额下一轮立刻能用。
- **失败不丢**：任务不再由 `tick()` 等待，失败就拿不到返回值了。单标的失败照旧只写它
  自己的状态；**全局性错误**记进 `fatalError`，循环下一轮检查到就退出——「全局性错误
  必须让进程退出」这条硬约束因此没丢，代价是退出最多晚一个轮询周期（默认 15 秒）。
- **优雅退出**要一并等在途任务（`stop()` 里），否则退出时会留下半途而废的写库事务。

守这个行为的用例在 `apps/sync/tests/lifecycle.test.ts` 的「慢标的不堵住别人」：
一个用例守住「慢的卡着时快的照旧一轮一轮跑」，另一个守住「并发上限没被这次修复废掉」。
