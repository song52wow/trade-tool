# @trade-tool/executor

常驻止盈止损服务（v0.4.0）：**成交事件 → 净仓位 → ATR → 止盈止损条件单**。多空都支持。

```
Binance 用户数据流（listenKey）
      │  同一 symbol 串行处理
      ▼
判定：是自己挂的单吗 → 是则记结算（另一张由交易所撤销）
      │ 否
      ▼
流内增量净额（启动 / 每次重连后由 positionRisk 播种）：
      ├── = 0      → 工具外平仓：未终结记录收敛为 cancelled
      ├── 方向相反  → 减仓，忽略（由它自己的单触发）
      └── 方向一致  → 新开仓（BUY 开多 / SELL 开空），继续
      ▼
该标的是否已有未终结保护？→ 是则跳过并留 warn（不叠第二套 closePosition）
      ▼
占坑 risk_bracket（exchange + symbol + entryOrderId）── 冲突即「事件重放」，跳过
      ▼
quant_data risk-atr（按成交时刻，只用库内已收盘的连续 1m）→ ATR(14)
      ▼
deriveBracketPlan：SL = 入场 ∓ 2×ATR，TP = 入场 ± 3×ATR，两张都朝远离入场价对齐 tick
      ▼
挂 TAKE_PROFIT_MARKET，再挂 STOP_MARKET（closePosition=true）→ 回填单号，state=armed

另有一条旁路：ACCOUNT_UPDATE → 覆盖本地净仓位（校正，不参与判定）
```

**为什么方向判据是净仓位而不是成交方向**：只做多时「SELL = 减仓」成立，
支持做空后它就错了——开空仓也是 SELL，而交易所的净仓位才是事实。

**净仓位为什么是「流内增量」而不是每次查接口**：`ORDER_TRADE_UPDATE` 在 USDⓈ-M 上
不带仓位（仓位在 `ACCOUNT_UPDATE` 里），而两类事件之间**没有顺序保证**，
所以既不能从成交事件里刨、也不能等账户事件。逐笔累加与交易所净额等价，且不依赖事件顺序、
不需要每笔出网。完整理由见 AGENTS.md §6.3 第 7 条与 `packages/core/src/net-position.ts`。

`handleFill` 的返回值是**可见的处理结论**（日志与测试都靠它区分「为什么没设单」）：
`ignored` / `settled` / `external-close` / `skipped-existing-bracket` / `duplicate` /
`partial-skipped` / `armed` / `failed`。

**启动时先校时钟**：本机时钟与交易所差 1 秒就会让每个私有请求吃 -1021（挂单、撤单、
对账全在里面）。`/fapi/v1/time` 是无签名的，时钟不准时依然可用，因此用它测量偏移，
并在启动日志里打出来——补偿不可见就等于没补偿。详见 `packages/core/src/clock-skew.ts`。

- `src/service.ts` — `createExecutorService()`：事件判定、幂等、下单与失败回滚。
  全部依赖（pool / 下单 / ATR）都是注入的。单轮行为用替身测（**不连 PG、不出网**）；
  跨轮累积用真库测，见下面「测试」一节。
- `src/atr.ts` — ATR 取数适配。指标公式只在 `quant_core`；这里只把控制信息交给
  `python -m quant_data risk-atr`，K 线不经 stdout（R-2.1）。
- `src/main.ts` — 进程入口（`bin: trade-tool-executor`）。默认 `executor.enabled = false`，
  不开就不启动；缺密钥直接拒绝启动。
- `src/alert.ts` — 对账报告 → 告警条目（v0.8.0）。指纹只由「是什么事」决定
  （差异类型 + 标的 + 入场单号），**不含**本轮的具体数值——掺进去会让每轮都算新告警，
  冷却就形同虚设。
- `src/plan-execution.ts` — 执行 Agent 方案（v1.0.0）：认领 → 下单 → 回填三步状态机。

## 飞书告警（v0.8.0）

周期对账发现的差异会推到飞书（实现见 `packages/core/src/notify.ts`，规则见 AGENTS.md
§6.9）。四件事值得记住：

- **推的是「报告」，不是「处置」**：不改任何账本、不碰交易所。处置一律人工决定，
  与对账「只报告不动手」是同一条保证。
- **一轮合成一条**：一个裸仓常同时命中好几条判据（「没有止损单」+「有仓位没记录」），
  拆开推就成了「一个问题推了三遍」。
- **不刷屏**：同一件事在冷却期（默认 30 分钟）内只推一次；严重度变了立刻重推；
  差异消失时推一条「已恢复」。
- **设置每轮重新读**：通道在**每轮对账时**重新解析一次（库里优先、配置文件兜底），
  所以控制面改完设置**不必重启本进程**，下一轮（默认 5 分钟内）就用新值。
  这与交易所凭据不同——凭据是启动时读的，改了要重启。
- **还有两类交易事件**：止盈止损挂单成功（附预估收益/预估亏损）、一轮买卖完成
  （附实际盈亏，已扣手续费）。金额一律 USDT；盈亏公式只有一份
  （`packages/core/src/pnl.ts`），库里只存**事实**（累计平仓量/成交额/手续费）。
- **每条推送都带订单号**（2026-10-22 加）：挂单成功带「入场 / 止盈 / 止损」三个号，
  一轮完成带「入场 / 出场」两个号，对账差异带交易所那侧与本地记的那侧的条件单号。
  差异说的是「本地的单和交易所的单对不上」，**单号就是排查那件事的钥匙**——
  拿着它去交易所的订单记录里查，不用靠「哪个标的、什么时候、什么价」去猜。
  一个单号都没有时**不留空括号**。
- **算不出来就说算不出来**（2026-10-22）：没拿到出场成交额时，卡片写「出场价没拿到 /
  盈亏算不出」，**不显示 0，也不拿 0 凑一个看着精确的假数**——
  `(0 − 入场价) × 数量` 就是一个巨大的假亏损（实测把一笔 0.3 USDT 的亏损显示成 194 USDT
  的盈利，原因是成交价取错了币安事件里的字段，详见 AGENTS.md §10.3）。

## 为什么是两次下单而不是一次

Binance U 本位永续**没有**单请求 OCO：`/fapi/v1/order/oco` 已下架，官方 TP/SL 走 algo
条件单。本服务挂 `STOP_MARKET` + `TAKE_PROFIT_MARKET`（都带 `closePosition=true`），
**仓位平掉后剩余那张由交易所自动撤销**——撤销关系在交易所侧，本地不轮询、不盯市。

⚠️ **v0.7.0 的分批形态部分推翻了上面这句保证**，照实说明：

| 形态                             | 止盈单                    | 仓位归零时另一张自动撤销？ |
| -------------------------------- | ------------------------- | -------------------------- |
| 不分批（`takeProfit1Ratio = 0`） | `closePosition`           | **是**，与 v0.4.0 完全一致 |
| 分批（`0 < ratio < 1`）          | `quantity` + `reduceOnly` | **否**，改由本地撤         |

原因是官方明确 `quantity` 与 `closePosition` **互斥**（同时发是 `-1106`），而带数量的单
只认数量，仓位已经是 0 时它不会自己消失。因此分批形态下：**止损单仍然是 `closePosition`**，
它继续保护减仓后的剩余仓位（这也是第一段成交后不必重挂止损的原因）；但**止盈单要由本地在
净额归零时撤**，且**进程不在时无人撤**。补偿手段是对账的 `unexpected-take-profit-order`
（只报告，不自动处理）。

**止盈倍数只有一个**（v0.9.1 起，`takeProfitAtrMult`）：它是「这次要卖的那部分，
涨到离入场多远就卖」——不分批时卖全部，分批时先卖减仓的那部分。
`takeProfit1Ratio = 1` 与 `0` 逐字等价，因此在服务端归一到 `0`。
`risk_bracket.take_profit` 记的**永远是实际挂出去的那张单**的价，因此页面显示的
「止盈价」与交易所上的单永远对得上。

移动止损（`0 < ratio < 1` 时剩余仓位的唯一自动出口）由 `src/trailing.ts` 的独立定时器
负责，与周期对账**分开**：对账是纯只读的，而移动止损要挂单撤单，合并会让「对账绝不动手」
这条保证失守。

先后顺序是刻意的：**先止盈后止损**。反过来若止损失败，我们就有一张撤不掉的止盈单，
仓位从此没有止损。若第二张没挂上，第一张会被主动撤掉。

### 止损单号带档位序号：挪单必须有新号（2026-10-22 修）

Binance **不允许同时存在两张 `clientAlgoId` 相同的挂单**（重复直接被拒：
`ClientOrderId is duplicated.`）。

于是每一档止损单必须有自己的号：格式 `rsk-<tp|sl><档位序号>-<入场单号>`。
0 号沿用旧格式（`rsk-sl-<入场单号>`），交易所上已经挂着的那张单不必改号。

**号先占后用**（`reserveTrailStep`）：每次下单尝试先占一个新号，哪怕那次下单最终失败。
换档失败时下一轮要重挂，沿用同一个号会再撞「重复」——重试永远失败。

### 挪单顺序是「先撤旧、再挂新」（2026-10-22 实测后改）

原先写的是「先挂新、再撤旧」，理由是「先撤后挂会造出无保护窗口」。
**那个前提在 Binance 上不成立**：同一标的、同一方向**只允许存在一张 `closePosition` 条件单**，
实测（Demo Trading）报错：

> `An open stop or take profit order with GTE and closePosition in the direction is existing.`

而条件单**没有改价接口**（`PUT /fapi/v1/order` 只支持 LIMIT，条件单已迁到 Algo 端点），
所以想换价只能「撤一张、挂一张」。代价是两次调用之间的短暂无保护窗口
（一次 API 往返量级）——与「止损永远停在入场那一档、移动止损整条线空转」相比小得多。

三条兜底：

| 情况                  | 处置                                                           |
| --------------------- | -------------------------------------------------------------- |
| 撤旧失败              | **不中断**，继续挂新：旧单可能还在（撤单报错），也可能已经没了 |
| 挂新失败              | **立刻用旧价挂回去**（撤旧已成功时仓位是裸的）                 |
| 挂新失败 + 恢复也失败 | 裸仓：记可见原因，等对账的 `missing-stop-order`（紧急）报出    |

挂新失败而恢复成功时，账面要指向**恢复出来的那张单**（`sl_algo_id` 会变，
价不变、档位不推进）——否则对账会拿一个已失效的单号去比价。

踩过的坑（2026-10-22 实测）：号当时只由入场单号派生，于是**每一次挪单都被拒**，
移动止损一次都没挪成。而它**看不出任何异常**：止损单在交易所上（`missing-stop-order`
不报）、触发价与本地一致（`price-mismatch` 不报），三方全绿。

因此库里多两列（迁移 `016`）：

| 列            | 含义                              |
| ------------- | --------------------------------- |
| `trail_step`  | 占用了几个止损单号（每次尝试 +1） |
| `trail_moves` | 成功换过几档（真的挪了才 +1）     |

两者的差值 = 「有几次换档尝试没成功」。这是**唯一**能看见「移动止损在空转」的信号，
对账据此判 `trail-move-failed`（注意级：仓位仍受止损保护，不是裸的）。
顺带它也回答了「挪过几次」：`trail_moves` 就是。

⚠️ **测试里的假交易所必须校验单号唯一性**。这个缺陷能活这么久，正是因为假交易所不校验——
「连挪三档」的端到端用例一直是绿的，而真交易所上第一挪就被拒。

### 持仓期极值取不到时（2026-10-21 修）

`risk-atr` 一次调用同时回 ATR 与持仓期极值（v0.7.0 R-6.2）。**「持仓期内一根已收盘 K 线
都没有」是刚开仓的常态**——成交后几秒内没有任何一根 K 线收盘，极值必然取不到。

这种情况**只回 `extreme: null`，不抛错**：抛错会把同一次调用里的 ATR 一起带走，
调用方只能当成「ATR 不可用」而拒绝下单，而成交事件不会重放——于是**新开仓永远挂不上
保护单**，仓位从此裸奔。

于是两条路径分开处置：

| 场景               | 处置                                               |
| ------------------ | -------------------------------------------------- |
| 刚成交，要挂保护单 | 极值用不上 → **照常按 ATR 挂出止盈与止损**         |
| 移动止损这一轮     | 极值用不上 → **本轮不移动、保留上一档** + 可见原因 |

「本轮不移动」写进 `trail_last_error` 并记日志：仓位仍受上一档止损保护，所以它比
「本轮失败」轻。⚠️ 两者不许混成一个码（v0.7.0 R-6.5）。

### 第一段成交之后：事实先落库、推进可重试（2026-10-21 修）

第一段止盈成交之后要发生三件事，**顺序不能换**：

| 步  | 做什么                                           | 落在哪                                     |
| --- | ------------------------------------------------ | ------------------------------------------ |
| 1   | **记「TP1 成交过」这个事实**（幂等）             | `recordBracketTp1Fill`：写 `tp1_filled_at` |
| 2   | **推进阶段** `partial_armed` → `trailing`        | `markBracketTrailing`：只写阶段与观测      |
| 3   | **把止损真的挪到新的一档**（挂新 → 撤旧 → 回填） | `moveTrailStop` → `markBracketTrailMoved`  |

第 1 步与「能不能算出移动止损」**无关**：极值取不到时，成交价 / 数量 / 手续费也必须记下来，
否则盈亏少算一段，而且**没有任何东西能证明「TP1 成交过」**——没有证据就没有重试，
记录会永远卡在 `partial_armed`，止损再也不跟着价格上移。

第 2 步与第 3 步是**两件事**：`trail_stop_price` 记的是**交易所上那张止损单现在的价**，
新档要等订单真的挂上之后才写（第 3 步）。于是「阶段推进了、价位还没挪」这一格是**可修**的
（定时器下一轮接着挪），而「库里写了新档、交易所还挂着旧单」那一格**谁也修不了**。

**移动止损定时器的工作集合有两类行**：

- `trailing` —— 已经在移动止损里的；
- `partial_armed` 且 `tp1_filled_at` 非空 —— **TP1 已成交但当时没推进成功**的。

第二类就是「已提交但没做完」的意图，定时器有权续做（v0.7.0 R-4.3 的续做，不是修复对账发现的漂移）。
⚠️ `partial_armed` 但 `tp1_filled_at` **为空**的行**不在**集合里：那是「TP1 还没成交」，
属于进场保护，止损不该被移动。

**成交事件路径与定时器共用同一对函数**（`markBracketTrailing` / `markBracketTrailMoved`）——
同一个动作有两份实现，迟早会有一份先坏掉。

## 让模型决定档位（v0.9.0，默认关闭）

`executor.llm.enabled = true` 时，每笔买入成交会先问一次模型要档位，再挂单。
实现分三处：

| 文件                                | 职责                                         |
| ----------------------------------- | -------------------------------------------- |
| `packages/core/src/llm-decision.ts` | 契约与纯函数：输出解析、范围校验、提示词构造 |
| `packages/data/src/llm.ts`          | HTTP 客户端（OpenAI 兼容协议，硬超时）       |
| `src/decision.ts`                   | 编排：调用、降级、可见性                     |

**模型只输出倍数，不输出价格**。价格仍由 `deriveStagedPlan` 算——这让价格计算保持可复现的
纯函数，也让 tick 对齐与「止损止盈必须分居入场价两侧」这两条判据保持**一份实现**。

模型的输出过与 `executorSchema` **同一份**取值范围的 zod 校验。越界**不是静默截断**，
而是拒绝这一份并降级。

三条降级路径（超时 / 报错 / 越界 / 档位自相矛盾）都落到同一个地方：
**按 `risk_policy` 的档位挂单**（仓位已经成交，不挂止损单就是裸仓），
同时把 `decision_source='config-fallback'` 与 `decision_fallback_reason` **落库**，
并推一条 `llm-fallback` 告警。`executor.llm.fallbackToPolicy = false` 时改为**不挂单**——
用户明确选了「宁可不挂，也不要在模型不可用时按不明档位挂」。

`risk_bracket.decision_source` 有四个值：`llm` / `config` / `config-fallback` / `agent-plan`。
后两者挂出去的价格可能一样，但性质不同——后者是需要人知道的故障。

⚠️ **裸仓窗口是这条路线固有的代价**：模型响应时间不可控，而它在「成交 → 挂单」之间。
`executor.llm.timeoutMs`（缺省 8 秒）是这个窗口的上限。

## 执行 Agent 方案（v1.0.0）

`apps/agent` 出的执行方案（`trading_plan.status = 'approved'`）由**本进程**消费并变成
真实订单。放在 executor 而不是 agent，是因为下单要用交易所凭据——凭据在这边，
且 executor 本来就持有私有接口、净仓跟踪与成交处理器。

三步：**认领 → 下单 → 回填**（`src/plan-execution.ts`）。

```
approved ──认领──> executing ──下单成功 + 回填──> executed
                        │
                        └──下单失败 + 原因──> failed
```

⚠️ **为什么中间要有「认领」**：下单成功但回填前进程崩掉的话，那一单已经真实存在，
而库里没有任何东西记着它。下一轮再跑一次就是**重复下单**——仓位翻倍，
而日志与库里都看不出异常。认领（`approved → executing`）是**幂等锚点**：
崩在中间时方案停在 `executing`，**不会被自动重试**（那一单到底下没下只有交易所知道），
执行器把它当「状态未知」报出来等人确认。宁可停下来问，也不要重复下单。

四条不许省的规矩：

1. **只支持市价进场**（`POST /fapi/v1/order`，回执 `orderId`）。
   限价单可能永远不成交，而不成交的仓位**没有止损保护**。
   限价方案在**批准时**就被拒绝（控制面与 CLI 都拒绝，agent 也不自动批准）。
   万一有 `approved` 的限价方案漏进来，executor 兜底**跳过**并写明原因——
   **不认领**：认领是幂等锚点，把一份永远执行不了的方案认领走只会让它卡在
   `executing` 变成「状态未知」，那比跳过更糟。
2. **自定义号带尝试次数**：`agt-p<方案id>-a<次数>`。Binance 不允许两张同 `clientOrderId`
   的挂单同时存在，沿用同一个号重试必然撞「重复」——与止损单号复用是同一个坑。
3. **已有仓位不叠加、已有未终结保护不开新仓**：条件单保护的是**整个净仓位**，
   重复挂会出现多组触发价互相撤销。
4. **方案档位优先于配置档位与模型决策**（`decision_source='agent-plan'`）。
   方案是**人批准时看到的**，配置档位随时会被改——让人批准的数和实际挂单的数
   必须是同一个。**价格仍由 `deriveStagedPlan` 按实际成交价算**
   （方案里的进场价是估算值）。

**反查方案失败不抛错**：抛错会让仓位裸奔（最贵的状态）。改为按配置档位挂单 +
显眼错误日志——仓位有保护，比档位完全对得上更要紧。

⚠️ **`executed` 只能由本进程写**：控制面与 CLI 只能置 `approved` / `rejected` / `expired`。
`executed` 必须同时带上单号与时刻（表上的 CHECK 守着），
否则页面上点一下就能造出一条「已下单」的假记录。

配置：`agent.execute.enabled = true` 时才装这个执行器与定时器
（`agent.execute.pollIntervalMs` 缺省 30 秒）。开关关着时 executor **压根不消费**方案。

## 幂等

用户数据流在 listenKey 续期与断线重连后会重放事件，而止盈止损是**会真实下单**的动作。
`risk_bracket` 的主键 `(exchange, symbol, entry_order_id)` 是唯一防线：先占坑再动手，
冲突即跳过。占坑后失败留下 `failed` 行 + `last_error`——宁可看得见的失败，
也不要「下单成功但没记下来，重连后再挂一次」。

## 测试

| 文件                               | 数据库              | 守的是什么                                                             |
| ---------------------------------- | ------------------- | ---------------------------------------------------------------------- |
| `tests/executor.test.ts`           | 替身                | **单轮**行为：该不该动、动了对不对、失败留不留原因                     |
| `tests/trailing-e2e.test.ts`       | **真库**            | **跨轮累积**：止损连挪好几档之后，库里那一行与交易所上那几张单还自洽吗 |
| `tests/plan-execution.test.ts`     | 替身                | **方案执行**：认领 → 下单 → 回填三步、幂等、不叠加仓位、限价被跳过     |
| `tests/plan-execution-e2e.test.ts` | **真库 + 假交易所** | **方案执行接缝**：真 SQL 的 WHERE 与表上的 CHECK 真的拦得住吗          |

**为什么方案执行也要一个真库版本**：替身版的 SQL 分支是手写的匹配，
真库的列一改它就悄悄失配，测试还绿。真库跑一遍，
「捞的是不是真的 `approved`」「回填会不会把没认领的行也改了」
「`executed` 却没有单号写得进去吗」这几条才是真的在守——
它们全是「替身版绿、真库红」的典型。

**为什么累积这件事要用真库**：替身的 SQL 分支是手写的匹配
（`sql.includes('SET trail_stop_price = $4, …')`），真库的列一改它就悄悄失配，测试还绿。
真库跑一遍，`risk_bracket_staged_check`（`trailing` 必须有 `trail_stop_price > 0`）、
`risk_bracket_state_check` 与那几条 UPDATE 的 WHERE 才是真的在守。

真库用例只把**行情与交易所**换成替身（`AtrProvider` 与 `OrderPlacer`）——真库、真迁移、
真 `createExecutorService`、真 SQL。真库设施来自 `@trade-tool/data` 的 `createTestSchema()`
（见 `packages/data/README.md`），随机 schema，绝不连生产库（AGENTS.md §8.1）。

`trailing-e2e.test.ts` 守的不变量：

- 止损**连挪三档**（60_100 → 60_300 → 60_600 → 60_900），一档都不许回头；
- 交易所上**始终只有一张**止损单，价就是库里那一档，账面单号就是它；
- 每次换档都是「先挂新、紧接着撤旧」，且**撤掉的正是上一档那一张**；
- 价格回落时档位**不放宽**；算出的止损位越过现价就本轮不动，并把原因写进 `trail_last_error`；
- **走定时器**（`startTrailingTimer`）也能连挪三档——生产环境里驱动移动止损的**唯一**入口就是它，
  绕开它去测「挪得对不对」，测不出「定时器根本没在跑」。

⚠️ 分批形态下第一段止盈单成交后**仍留在交易所**（带数量的单没有 `closePosition` 那个自动撤单
保证），要等本地撤——这是 v0.7.0 明确接受的取舍，由对账的 `unexpected-take-profit-order` 报告。
断言「交易所上只有一张单」时，数的是**止损单**，别把那张 TP1 算进去。

## 运行

```bash
cp .env.example .env        # 填 TRADE_TOOL_BINANCE_API_KEY / _SECRET
# 配置里 executor.enabled = true（会真实下单）
pnpm --filter @trade-tool/executor start
```

前置条件：目标标的的 1m K 线已被 `apps/sync` 同步到成交时刻附近——
ATR 只从库里读，库里没有就记 `RISK_ATR_UNAVAILABLE` 并拒绝下单，
**绝不**换周期或用 0 顶替（止损位等于入场价就是当场平仓）。
